## 2. 데이터 출처

| 패널 | API | 성격 |
|---|---|---|
| 좌 (연동 대상) | `GET .../tested-logical-databases/by-resource-id` | Test Connection이 **발견한** 논리 DB. 사실(fact), 읽기 전용 |
| 우 (연동 제외) | `GET .../excluded-databases/by-resource-id` | 운영자가 **설정한** 제외 정책. 정책(policy), 편집 대상 |

두 데이터셋은 서로 독립이다. 좌측에 없는 DB도 우측에 넣을 수 있고(직접 입력), 그것이 오류는 아니다. 저장은 `PUT`이며 **목록 전체 교체(full replace)** 다 — 우측에서 지우고 저장하면 상대 정책이 삭제된다.

## 3. 현재 인터랙션 플로우

### 3-1. 제외 추가 (좌 → 우)

```
좌측 항목의 [제외 추가] 클릭
   ↓  prefill() — 하단 폼의 database/schema 입력칸에 값만 채움   (:119-123)
   ↓  (사유 select를 필요하면 변경)
하단 [추가] 버튼 클릭
   ↓  add() — 그제서야 우측 draft 배열에 들어감                  (:125-151)
   ↓
[저장] 클릭 → PUT → GET 재조회                                   (:158-175)
```

**클릭 3회 + 시선 이동 2회**(좌측 → 하단 폼 → 우측)가 항목 1개당 필요하다.

### 3-2. 제외 해제 (우 → 좌)

```
우측 항목의 [삭제] 클릭
   ↓  remove() — 즉시 draft에서 제거                              (:153-156)
```

**클릭 1회.** 추가는 3회인데 제거는 1회다.

### 3-3. 직접 입력

하단 폼에 database(필수) / schema(선택)를 자유 입력한다. schema를 채우면 `SCHEMA` 범위, 비우면 `DATABASE` 전체 범위로 `type`이 자동 결정된다(`:142-143`).

## 4. 문제점

### P1. 제외 추가가 즉시 반영되지 않는다 — 최우선

`제외 추가` 버튼의 이름은 "추가"인데 실제로는 **입력칸 채우기(prefill)** 만 한다. 실제 추가는 하단 `추가` 버튼이다.

```ts
  const prefill = useCallback((item: TestedLogicalDatabase) => {
    setDatabase(item.databaseName ?? '');
    setSchema(item.schemaName ?? '');
    setFormError(null);
  }, []);
```

문제는 세 겹이다.

1. **라벨과 동작 불일치** — "제외 추가"를 눌렀는데 우측 목록이 안 변한다. 눌렀는지 확인하려면 하단 폼을 봐야 한다.
2. **비대칭** — 제거는 1클릭 즉시인데 추가만 3클릭 지연이다. 같은 화면에서 반대 방향 동작의 비용이 3배 차이난다.
3. **N개 처리 시 선형 반복** — 10개를 제외하려면 30클릭. 다중 선택 수단이 없다.

추가로, prefill은 폼을 **덮어쓴다**. 직접 입력하던 중 좌측 항목을 클릭하면 입력 중이던 값이 경고 없이 사라진다.

### P2. 설명이 부족하다

현재 모달에 있는 설명은 **2문장**이 전부다.

| 위치 | 문구 |
|---|---|
| `:198-200` | "연동 제외 정책은 저장할 때 목록 전체가 교체됩니다. 목록에서 지운 항목은 제외가 해제됩니다." |
| `:325-327` | "Schema를 입력하면 SCHEMA 범위, 비우면 DATABASE 전체가 제외됩니다." |

없는 설명:

| 없는 것 | 왜 필요한가 |
|---|---|
| **제외하면 무슨 일이 일어나는가** | 업무적 결과(스캔 대상 제외? 연동 자체 제외?)가 화면 어디에도 없다. 운영자가 결과를 모르고 정책을 바꾼다 |
| **`STG` / `DEV` / `TEMP` 각각의 뜻** | enum 원문 그대로 노출된다. 코드 주석도 "계약 어디에도 한국어 라벨이 없어 raw로 보여준다"고 인정한다(`:30`) |
| **좌측 목록의 출처** | "Test Connection이 발견한 것"이라는 맥락이 admin 모달에는 없다. 사용자향 모달에는 있다 |
| **직접 입력이 왜 필요한가** | 좌측에 있는 걸 고르면 되는데 왜 자유 입력칸이 있는지 설명이 없다. 오타 위험만 눈에 띈다 |
| **`DATABASE` / `SCHEMA` 범위 차이의 결과** | 입력 규칙만 있고("schema를 채우면 SCHEMA"), 범위가 넓고 좁음이 무엇을 의미하는지는 없다 |
| **전체 교체의 위험** | 1문장 있지만 평문이고, 저장 직전에 무엇이 지워지는지 확인할 방법이 없다(P3) |

⚠️ `STG`/`DEV`/`TEMP`의 한국어 의미는 **swagger에 description이 없다**(`install-v1.yaml:7525-7530`, enum만 선언). 임의로 라벨을 지어내면 안 되고, 오너 확인이 필요하다(§7 Q1).

### P3. 저장 전 변경 요약이 없다

전체 교체 방식인데 저장 버튼 옆에 **무엇이 추가되고 무엇이 지워지는지 표시가 없다**. `dirty` 여부만 계산해 버튼 활성화에 쓴다(`:178`). 되돌리기(초기화) 수단도 없다.

### P4. 검색이 없다

좌측 패널은 Test Connection이 발견한 논리 DB 전량이다. 수십 개인 경우 `max-h-[260px]` 스크롤 안에서 눈으로 찾아야 한다(`panel.body`, `:53`).

### P5. 오타 입력 무검증

직접 입력은 좌측 목록과 대조하지 않는다. 존재하지 않는 DB 이름도 그대로 저장된다. 중복만 막는다(`:133-136`).

## 5. 핵심 발견 — 원하는 패턴이 이미 코드베이스에 있다

**사용자향 Step 5 모달**(`app/target-sources/[targetSourceId]/_components/logical-db/LogicalDbModal.tsx`)이 같은 도메인을 다루면서 P1·P3·P4를 이미 해결해 두었다.

| 항목 | 사용자향 `LogicalDbModal` | Admin `LdbManageModal` |
|---|---|---|
| 좌→우 이동 | **클릭 1회 즉시 이동** (`moveToB`, `:54-60`) | 3클릭 (prefill → 추가) |
| 우→좌 이동 | 클릭 1회, 라벨 `복원` (`:62-76`) | 클릭 1회, 라벨 `삭제` |
| 검색 | **양쪽 패널 모두 있음** (`searchA`/`searchB`, `:40-46`) | 없음 |
| 변경 요약 | **푸터에 `변경사항 N건 · 추가 N · 제거 N`** (`:91-105`) | 없음 |
| 저장 버튼 | 변경 0건이면 비활성 (`:112`) | 동일 |
| 화면 설명 | "Test Connection으로 발견된 논리 DB와 제외 정책을 한 화면에서 관리해요." (`:147`) | 출처 설명 없음 |
| 직접 입력 | **없음** (발견된 목록에서만 선택) | 있음 (자유 입력) |
| 사유 선택 | **UI 없음** (`reasons` state는 있으나 화면에서 설정 불가) | select로 선택 가능 |

두 모달은 같은 API(`app/lib/api/logical-db.ts`)를 쓰면서 상호작용 문법이 다르다. **Admin 쪽만 구식이다.** 다만 Admin에만 있는 능력이 둘 있다 — 직접 입력, 사유 선택. 이 둘은 버리면 안 된다.

## 6. 개선 방향 (오너 지시 기준, 미확정)

오너가 지목한 순서:

1. **즉시 반영으로 전환** — 좌측 항목 클릭 = 우측에 바로 들어감. 사용자향 모달의 `moveToB` 문법과 통일. `제외 추가` 라벨은 동작과 맞게 조정.
2. **직접 입력은 유지하되 위치 이동** — 하단 상설 폼을 없애고, **우측 패널의 아이콘 트리거**로 직접 입력을 연다. 평상시엔 목록 선택이 주 동선, 직접 입력은 예외 수단으로 밀어둔다.
3. **설명 보강** — §4 P2 표의 빈칸을 채운다. 단, `STG`/`DEV`/`TEMP` 라벨은 오너 확인 전까지 지어내지 않는다.

동선상 함께 검토할 것: 변경 요약(P3), 검색(P4). 둘 다 사용자향 모달에 구현체가 있어 이식 비용이 낮다.

## 7. 오너 확인 필요

- **Q1.** `STG` / `DEV` / `TEMP`가 각각 무슨 뜻인가? 화면에 한국어 라벨을 붙일지, enum 원문을 유지할지? (계약에 description이 없어 임의 생성 불가)
- **Q2.** "연동 제외"의 업무적 결과는 무엇인가? PII 스캔 대상에서 빠지는가, 연동 자체가 안 되는가?
- **Q3.** 직접 입력은 어떤 상황을 위한 것인가? (Test Connection이 못 잡은 DB를 선제 등록? 다른 이유?)
- **Q4.** 사유 선택을 사용자향 모달에도 노출해야 하는가, Admin 전용으로 둘 것인가?
- **Q5.** 두 모달을 하나의 공용 컴포넌트로 수렴할 것인가, 문법만 맞추고 별도로 둘 것인가?
