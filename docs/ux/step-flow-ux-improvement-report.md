## 1. 현재 구조 요약

Step 1~7은 URL 라우팅 위저드가 아니라 **단일 URL + `processStatus` 상태 머신**이다.
`CloudTargetSourceLayout.tsx:52` / `IdcTargetSourceLayout.tsx:43`의 `px-10 pt-8 pb-20 space-y-6` 래퍼가
모든 스텝에서 아래 **고정 4겹 세로 스택**을 쌓는다.

```
┌──────────────────────────────────────────────┐
│ 페이지 헤더  AWS (aws)          [협업채널][인프라 삭제] │  24px 타이틀
├──────────────────────────────────────────────┤
│ ① Identity bar (Provider/Account/TF권한/Agent)   │  radius 14
├──────────────────────────────────────────────┤
│ ② "프로세스 진행 상태" 카드  ← 26px 타이틀        │  radius 20, ~150px
│    (7단계 스테퍼, display-only)                  │
├──────────────────────────────────────────────┤
│ ③ 가이드 카드 (amber)                           │  radius 12, ~180px
│    제목 + 문단 + 불릿 2개                        │
├──────────────────────────────────────────────┤
│ ④ 작업 카드  ← 26px 타이틀 (여기서부터 실제 작업)  │  radius 20
│    배너 + 테이블 + …                            │

└──────────────────────────────────────────────┘
```

- 실측: 1512×950 뷰포트에서 **작업 카드 타이틀이 뷰포트 세로 ~73% 지점**에서 시작.

## 2. 문제 진단

### P1. CTA가 fold 아래에 있고, 배치 문법이 스텝·프로바이더마다 다르다 — **심각도 상**

실화면 + 코드로 확인한 CTA 위치 현황:

| Step | 화면 | 주 액션 | 위치 | 근거 |
|---|---|---|---|---|
| 1 (Cloud) | 연동 대상 DB 선택 | 연동 대상 승인 요청 (primary) | **카드 최하단 우측** (fold 아래) / Run Infra Scan은 헤더 우측 | 캡처 1006 |
| 1 (IDC) | 연동 대상 DB 입력 | 연동 대상 추가 (primary) | **카드 헤더 우측** | 캡처 1020 |
| 2 | 승인 대기 | 전체 요청 취소 (danger-outline) | 카드 최하단 우측 | 캡처 1007 |
| 3·4 | 반영중 / Agent 설치 | 없음 (자동 진행) | — | 캡처 2001/1008 |
| 5 | 연결 테스트 | **Run Test (primary 파랑, 헤더)** + **완료 승인 요청 (primary 파랑, 최하단)** | 헤더와 최하단에 파랑 2개 동시 | 캡처 1010/1024, `IdcStep5ConnectionTest.tsx:280-290`, `:347-352` |
| 6 | 완료 승인 대기 | 연결 테스트 재실행 (amber) | 카드 최하단 우측 | 캡처 1011 |
| 7 | 연동 완료 | 인프라 변경 + 연결 테스트 재실행 (amber 2개) | **테이블 위(body top)** | 캡처 1012, `InstallationCompleteStep.tsx:59` (`flex justify-end gap-2 mb-3`) |

코드 레벨로도 세 가지 패턴이 혼재한다: 카드 헤더(`IdcStep5…:287`), body 상단 `mb-3`(`IdcStep7Complete.tsx:42`, `InstallationCompleteStep.tsx:59`), body 하단 `mt-4`(`IdcStep1TargetInput.tsx:303`, `IdcStep2WaitingApproval.tsx:103` 등). sticky/고정 액션 존은 어디에도 없다.

**결과**: 사용자는 스텝마다 "이번엔 버튼이 어디지?"를 다시 학습한다. 특히 Step 5는 시각 무게가 같은
파란 primary 두 개가 대각선 반대편에 있어 다음 행동이 무엇인지 화면이 답하지 않는다.

> 위반 규칙: `primary-action`(화면당 primary 1개, 보조는 시각적 종속) · `visual-hierarchy`

### P2. 작업보다 안내가 먼저 — 고정 크롬 3겹이 fold를 소모한다 — **심각도 상**

- 스테퍼 카드(②)는 세로 ~150px를 쓰지만 전달 정보는 "현재 N/7단계" 하나다. 클릭 내비게이션도 없는 display-only인데,
  실제 작업 카드와 동일한 26px 타이틀("프로세스 진행 상태")과 동일한 카드 뼈대를 갖는다 (`ProcessStatusCard.tsx:15-17`).
- 가이드 카드(③)는 ~180px로 매 스텝 등장하며, 대기 스텝(2·3·6)에서는 작업 카드가 할 일이 없는데도 안내가 화면 절반을 차지한다.
- Step 4는 작업 카드 안에 서브스텝 타일 3개(연한 초록/파랑/회색 박스)가 또 있어 **카드 안 카드 안 카드** 3중 중첩이 된다.

> 위반 규칙: `content-priority`(핵심 콘텐츠 먼저) · `whitespace-balance` · `progressive-disclosure`(도움말은 필요 시)

### P3. 같은 말을 4~5곳에서 반복한다 — **심각도 중**

Step 2(1007) 한 화면에서 "승인을 기다리는 중"이라는 동일 정보가:

1. 가이드 카드 제목 "승인자의 검토를 기다리고 있어요"
2. 작업 카드 부제 "요청하신 DB 목록을 관리자가 확인하고 있어요"
3. 파란 정보 배너 "관리자 승인을 기다리고 있어요. 평균 1영업일 내 검토되며…"
4. 우상단 배지 "승인 대기"
5. 스테퍼 현재 라벨 "연동 대상 승인 대기"

**5회 반복**된다. Step 3(승인됨/반영중)·Step 6(최종 승인 대기)도 같은 패턴. 중복 서술이 카드 수를 늘리고,
정작 새 정보(요청일시, 대상/비대상 건수)가 반복 문장 사이에 묻힌다.

### P4. 카드 계층 신호가 없다 — 모든 카드가 동급으로 보인다 — **심각도 상**

- **타이틀 동급**: 크롬 카드(②)와 작업 카드(④)가 같은 `cardStyles.cardTitle`(26px extrabold, `theme.ts:274`)을 쓴다.
  한 화면에 26px 타이틀이 2개 이상 → 시선의 앵커가 없다.
- **계층 역전**: 페이지 h1(`pageHeaderTitleStyle`, 24px, `theme.ts:334`)이 카드 타이틀(26px)보다 **작다**.
- **타입 래더 단절**: 26 → 13.5(부제, `theme.ts:276`) → 13(테이블 헤더) → 12(캡션). 중간(16~20px)이 없어
  "카드 안 섹션"을 표현할 수단이 없다. admin 파이프라인에는 이미 `pipelineText.sectionTitle`(20px, `theme.ts:851`)이
  있으나 target-source 화면은 쓰지 않는다.
- **표면 문법 불일치**: radius 20(카드, `theme.ts:256`) / 14(identity bar) / 12(가이드 카드, `GuideCardChrome`) 혼재,
  그림자도 2종 — 어떤 박스가 같은 급인지 형태로 구분되지 않는다.

> 위반 규칙: `font-scale`(일관된 모듈러 스케일) · `heading-hierarchy` · `visual-hierarchy` · `elevation-consistent`

### P5. (보조) 상태별 액션 스타일 불규칙 — **심각도 하**

Step 5는 primary 파랑 2개, Step 6은 amber 1개, Step 7은 amber 2개가 나란히 — 주/보조 구분이 색·위치 어느 축에서도
일관되지 않는다. P1의 규칙을 세우면 함께 해소된다.

## 3. 개선안

### A. 우측 가이드 패널 + [가이드 | 진행 내역] 탭 — *사용자 제안 채택, 구조 개선의 축*

가이드 카드를 세로 스택에서 **우측 고정 패널(약 340px)**로 이동한다.

```
┌────────────┬──────────────────────────────┬───────────────┐
│ Service    │ 페이지 헤더 + 컴팩트 스테퍼 스트립   │ ┌───────────┐ │
│ List       ├──────────────────────────────┤ │[가이드|진행내역]│ │
│ (기존 좌측) │ Identity bar (유지 or 헤더 병합)   │ │           │ │
│            ├──────────────────────────────┤ │ 현재 스텝    │ │
│            │ ④ 작업 카드 ← 유일한 26/20px 타이틀│ │ 가이드 본문  │ │
│            │    배너·테이블 (fold 안에 7~8행)  │ │ 불릿·링크   │ │
│            │                              │ │           │ │
│            │ ──────────────────────────── │ │ (진행 내역:  │ │
│            │        [보조]  [Primary CTA]  │ │  요청→승인→  │ │
│            │        ↑ 카드 하단 고정 액션 바   │ │  반려 타임라인)│ │
└────────────┴──────────────────────────────┴───────────────┘
```

- **가이드 탭**: 기존 `GuideCardContainer`의 slotKey 콘텐츠를 그대로 이관. amber 강조는 패널 헤더 액센트로 축소.
- **진행 내역 탭**: 연동 요청/승인/반려/재시도 이력 타임라인. **초기엔 하드코딩 mock으로 충분** (이력 API는 후속).
  스텝 전이 시점 데이터(`요청일시 2024-01-18`, `승인일시 2024-01-19` 등)는 이미 화면 곳곳에 흩어져 있으므로 수렴처가 생기는 효과.
- 효과:
  - 세로 스택 4겹 → 3겹(추후 B 적용 시 2겹). 작업 카드가 fold 위로 올라옴.
  - 가이드가 스크롤과 무관하게 항상 옆에 → 작업 중 참조 가능(현재는 스크롤로 가이드가 사라짐).
  - P3의 중복 서술이 자연 해소: "왜/얼마나 걸리나/문의처"는 패널 담당, 작업 카드는 "상태 + 데이터 + 행동"만.
- 구현 노트:
  - `ProjectDetail.tsx`의 우측 컬럼을 `grid grid-cols-[1fr_340px]`로 분할하면 Cloud/IDC 양 패밀리에 한 번에 적용된다
    (개별 스텝 파일 수정 불필요, 스텝별 가이드는 이미 slotKey로 주입되고 있음).
  - Desktop-only 앱이므로 반응형 부담은 낮음. 좁은 창 대비 패널 접기 토글 정도만.

### B. 진행 상태 카드 → 컴팩트 스트립

- `ProcessStatusCard`의 26px 타이틀 **"프로세스 진행 상태" 제거** — 번호 원 + 라벨의 스테퍼는 자기설명적이다.
- 카드 헤더/바디 패딩(28px)을 걷어내 ~150px 카드 → **~72px 스트립**으로. 페이지 헤더 바로 아래 배치.
- 대안: 우측 패널 '진행 내역' 탭 상단에 **수직 스테퍼**로 통합(단계와 이력은 같은 정보 축). 이 경우 본문 스택은
  identity bar + 작업 카드만 남아 회수 효과 최대. 단, 스텝 위치의 상시 가시성은 낮아지므로 1차는 스트립화를 권장.
- ⚠️ 제약: `docs/reports/sit-step-polish`에서 스테퍼 모션 로직은 frozen으로 선언됨 — **모션/전이 로직은 보존**하고
  배치와 크롬(타이틀·패딩)만 변경할 것.

### C. 액션 존 규칙 통일

| 규칙 | 내용 |
|---|---|
| C-1 | **스텝당 primary 1개**. Step 5의 Run Test는 secondary(soft)로 강등, "완료 승인 요청"만 primary 유지 |
| C-2 | **다음 단계 전이 액션 = 작업 카드 하단 고정 액션 바** (우측 정렬, `border-t` 구분). 카드가 길면 액션 바만 `sticky bottom-0` + 배경/보더로 항상 노출 |
| C-3 | **반복·보조 액션(Run Test, 재실행, 인프라 변경, 불러오기) = 카드 헤더 우측** 고정 |
| C-4 | disabled 사유 ※문구는 액션 바 좌측에 유지 (현재 Step 5 패턴이 좋음 — 액션 바로 흡수만) |

- Step 7의 amber 2개(인프라 변경/재실행)는 보조 액션이므로 C-3에 따라 헤더 우측으로.
- 공용 `CardActionBar` 컴포넌트 하나로 캡슐화하면 이후 스텝 추가 시 문법이 강제된다.
- sticky 적용 시 `fixed-element-offset` 규칙대로 카드 하단 패딩 확보.

### D. 타이포·표면 계층 재구성

- 목표 래더: **페이지 24 > 카드 타이틀 20 > 카드 내 섹션 16 > 본문 13.5~14 > 캡션 12**
  - `cardTitle` 26 → 20: admin의 `pipelineText.sectionTitle`(20/600) 문법을 target-source에 도입. 24px 페이지 타이틀과의 역전 해소.
  - B에서 스테퍼 타이틀을 제거하면 "26px 두 개" 문제는 자동 소멸 — 남는 작업 카드 타이틀만 20px로 조정.
- radius 통일: 본문 표면은 20 고정(카드), 패널·identity bar도 20(또는 16 한 단계만 허용)으로 정렬. 12/14/20 혼재 해소.
- 서브스텝 타일(Step 4)은 "카드"가 아니라 **플랫 리스트 + 상태 아이콘**으로 강등해 중첩 1단계 축소.

### E. 상태 메시지 단일화

- 원칙: **상태 서술문은 화면에 1곳** — 작업 카드의 배너(파란/초록)가 담당.
- 카드 부제는 서술 대신 데이터 요약(요청일시 · 요청자 · 건수)으로.
- "평균 1영업일", "문의처", "다음에 일어날 일"은 가이드 패널로 이동.
- 배지(승인 대기 등)와 스테퍼 라벨은 유지 — 스캔용 신호로 역할이 다름.
