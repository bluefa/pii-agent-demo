## 채택 근거

다섯 안(A 2단 평서 스트립 · B 명명 블록 + 2단 스트립 · C kv 4열 · D 한 줄 압축 · E 스트립 + 오버레이)을
같은 축으로 점수 냈고, 표에서 B(9.5)와 C(9.5)가 나란히 섰다. 표의 추천은 B 였다 — C 가 36px 더 높고
「4열」 규칙에 SA 열 병합이라는 예외를 하나 만들기 때문이다. **오너가 C 를 골랐다.**

C 가 가진 것:

- 사실이 몇 개든 **셀만 늘어난다**. 프로바이더 분기가 "어느 셀을 그리나" 하나로 줄어든다.
- 라벨이 값 **위**에 있어 짝이 이미 붙어 있다 — 열이 넓어져도 라벨·값이 갈라지지 않는다.
- P4 를 마저 닫는다: 블록 이름 「연동 대상」이 14px 계단을 만든다 (실측 census — 16 ×1 / 14 ×11 / 12 ×24).

## 오너 판단 3건 — 채택한 답

| # | 질문 | 답 |
|---|------|-----|
| Q1 | 서비스 이름을 경로에서도 뺄까 | **경로는 유지**. 크럼은 "무엇"이 아니라 "어디"를 말하고, 형제 화면(R1)도 이름을 경로에 남긴다. 레일의 서비스 블록만 접힘으로 갔다 |
| Q2 | 「상세 정보」 큐 위치 | **블록 머리 오른쪽 끝**. 큐가 자기가 여는 블록과 같은 줄에 서야 무엇이 열리는지 말한다 |
| Q3 | Azure 구독·테넌트 | **둘 다 스트립** (오너 2026-08-26). 처음 제안은 「구독만」이었다 — UUID 두 개가 한 줄에서 468px 를 쓴다는 이유였는데, 4열 그리드는 값 폭이 아니라 **셀 수**로 서는 배치라 그 근거가 성립하지 않는다. 둘이 나란히 서면 Azure 의 1행이 정확히 4칸으로 찬다 (실측 233 · 231px, 240px 열에 7px 여유) |

## 후속 지시 — 경로 한 줄 (2026-08-26)

크럼(`서비스 운영 / IDC / #1020`)과 제목(`Target Source 운영 #1020`)이 두 줄로 같은 말을 하고 있었다.
오너 지시: **한 줄로 정리하고, 「Target Source 운영」을 과하게 강조하지 않는다.** Linear 의 FrontMeta 처럼
마디마다 값의 **종류**를 태그가 먼저 말한다.

```
서비스 운영  /  [서비스 코드 CPN]  /  Target Source 운영  /  [Target Source #1642]
└ 파란 낱말                              └ 짙은 낱말
```

마디는 **「화면 이름 · 그 화면의 식별자」 짝**으로 두 벌 선다 (오너 2026-08-26). 지나온 화면의 이름만 파랗다 —
파랑은 이 팔레트에서 "누를 수 있다"이고, 그 옆 태그는 정체성이라 색을 쓰지 않는다: 이동은 낱말이 지고 값은
태그가 진다. 코드 태그 자체를 링크로 만들고 hover 에서만 면을 내리던 첫 판은 폐기됐다 — 링크를 알아볼 방법이
hover 밖에 없었다.

- 「Target Source 운영」 16/700 → **14/600** (서비스측 `crumbRoot` 와 같은 계단). 마스트헤드에 16px 은
  남지 않는다 — 지시 4 는 허용 집합이지 필수 집합이 아니다.
- 서비스 **이름**이 경로에서 빠졌다. Q1 은 "경로는 유지"였지만 그때 경로에 있던 것은 이름이었고,
  이름은 라벨이라 대조에 쓰이지 않는다. 경로에 서는 것은 **식별자** 둘 — 서비스 코드와 대상 번호.
  이름은 「상세 정보 → 서비스 → 이름」에 그대로 있다. 지시 3("서비스 이름 같은 건 다 감추고")이
  여기서 완전히 닫힌다.
- 「서비스 운영」은 그 서비스의 운영 화면으로 가는 파란 낱말이다 — 옛 크럼이 지던 길 그대로. 조상 마디라
  12/600 이고, 서 있는 화면(`pathRoot` 14/600)보다 한 단 작다: 지나온 곳과 서 있는 곳의 차이가 곧 경로의
  순서다. 실측 4.69:1.
- 마디 태그는 `codeChip` 을 --pl-* 로 옮긴 것: gray-200 면 + border-strong 획. 실측 라벨 6.20:1 ·
  값 14.32:1 (칩 면 기준).
- 실측: 마스트헤드 259 → **237px**, 탭 y 282 → **259**. 활자 인구조사 **14 ×10 / 12 ×25 — 그 밖 0개**.

## CSP 마크 — 지시 5 를 문자 그대로 따르지 않은 이유

16px 슬롯에서 AWS 워드마크의 글자 높이는 슬롯의 0.32배 = **5px** 이다. 서비스측이 20 → 28px 로 올린
근거가 정확히 이것이고, 그 결정은 이미 오너 지시(8차)로 내려져 있다. 대신 **활자 램프의 배수**로 맞췄다:
시안 C 는 마크가 한 줄 안(블록 머리)에 앉으므로 **20px** — 운영 대시보드 `identityGlyphMark` 의 값이고
새로 만드는 수치가 아니다. 24px(옛 제목 줄)은 어느 쪽도 아니어서 버렸고, 이 화면의 마크가 하나로
줄면서 P7 이 닫혔다.

### 남긴 것 · 열린 것

- 접힘의 「식별자」 그룹은 스트립과 값이 겹친다 (GCP 는 SA 전문이 두 번). **의도한 중복**이다 — 스트립은
  훑는 자리, 접힘은 복사하는 자리이고, 지시 6("많은 정보")이 풍성한 접힘 쪽을 가리킨다. 걷어내려면
  `OpsDetailFold` 의 `identifiers` 를 "스트립이 줄인 값 + 스트립에 없는 값"으로 좁히면 된다.
- 접힘을 열면 탭이 231px 내려간다. 시안 E(우측 오버레이)만 이걸 0 으로 만들 수 있고, C 는 디스클로저의
  본래 동작을 따른다.
- 열 폭 240px 는 1440 에서 고른 값이다. `minmax(0,240px)` 이라 좁아지면 같이 줄고 넘치지 않는다.
- **로딩 스켈레톤이 예약하는 kv 행은 2행**인데 「관련 페이지」 셀(2열)이 붙으면서 AWS(TF 위임) · GCP 는
  3행이 된다 — 도착 시 탭이 52px 내려간다. 정확한 상수가 없다: 셀 수가 프로바이더마다 달라 1(IDC) ·
  2(AWS 수동 · Azure) · 3(AWS+TF · GCP) 로 갈린다. 3행으로 올리면 앞의 셋이 반대로 올라온다. main
