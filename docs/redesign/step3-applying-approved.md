# Step 3 · 연동 대상 반영중 화면 리디자인

> 작성 2026-07-31 · 근거 화면 `/pass/target-sources/2001` (AWS) · `/2003` (Azure) · `/2008` (GCP)
> 선행 기록: `docs/redesign/step2-approval-waiting.md` (PR #590)

> `useApprovalTableState` / `WaitingApprovalCard`(공유분) / `shared/MetaField`(신설)

Step 2에서 이미 공유 컴포넌트로 반영된 것(컬럼 순서, `요청 대상 여부` 헤더, 값 `대상`/`제외`,

**이 화면의 결론은 "Step 3 전용 UI를 만들지 않는다"였다.** Step 3만 갖고 있던 세 가지(연동 이력
컬럼, 연동 상태 필터, 툴바 세그먼트)가 전부 삭제로 끝나면서, Step 2와 같은 카드가 승인 메타만
바꿔 끼운 형태가 됐다. 삭제 339줄 / 추가 117줄.

## 1. 🐞 `연동 이력` 컬럼 — 계약에 없는 값이었다

**증상**: 4행이 전부 주황 `Pending` 태그. 정보는 없고 색만 튀었다.

**원인**: `integration_status`는 `docs/swagger/install-v1.yaml` **어디에도 없다**. 값을 만드는 곳은
`lib/bff/mock/confirm.ts`의 `deriveIntegrationStatus()` 하나뿐 — 목이 발명한 필드다.
실 BFF에서는 전 행이 `—`로 뜨고, 아래 배너의 `N건 중 0건 완료`는 **영원히 0건**이었다.

| | Before | After |
|---|---|---|
| `연동 이력` 컬럼 | `Integrated`(녹) / `Pending`(주황) / `—` | **삭제** |
| 툴바 `연동 상태` 필터 그룹 | `Integrated (N)` / `Pending (N)` / `제외` | **삭제** |
| 배너 진행 카운트 | `전체 7건 중 0건 완료` | **삭제** |
| 대상/사유 컬럼 | `요청 대상 여부 / 제외 사유` 병합(사유가 알약 아래 쌓임) | **`요청 대상 여부` + `제외 사유` 분리** (= Step 2와 동일) |
| `WaitingApprovalTable` variant | `waiting` \| `applying` | **prop 삭제** (분기가 사라짐) |

**좋아진 점**

- 없는 사실을 있는 것처럼 그리던 컬럼이 사라졌다. 행마다 배지는 판정(`대상`/`제외`) 하나가 되어
  Step 2의 "행당 배지 1개" 예산과 같아졌다.
- 병합 컬럼을 유지할 이유가 `연동 이력`이 마지막 칸을 차지했기 때문이었다. 그게 없어지자
  Step 2의 컬럼 구성이 그대로 맞아떨어졌고 `variant` 분기 전체가 없어졌다.
- 이 컬럼을 지키던 테스트 4개가 전부 **계약에 없는 필터를 고정하는 테스트**였다. 지우고,
  "연동 상태 필터가 없을 것 / 연동 이력 컬럼이 없을 것"을 확인하는 회귀 테스트로 바꿨다.

> ⚠️ `integration_status`는 `lib/types.ts`·`lib/bff/mock/confirm.ts`에 아직 남아 있다.
> 이번엔 **노출만** 지웠다 — 목 데이터·타입 정리는 별도 작업(LIN-51 계열)이다.

## 2. 툴바 세그먼트 → 상단 타일 (Step 2와 동일)

| | Before | After |
|---|---|---|
| 카운트/필터 UI | 툴바 세그먼트 `전체 4 / 연동 대상 4 / 연동 제외대상 0` | **상단 타일 3개** (클릭=필터) |
| 용어 | 연동 대상 / 연동 제외대상 (#590 이전 표기) | **전체 요청 / 연동 요청 대상 / 연동 요청 제외대상** |
| Region 필터 | Step 3에서만 숨김 | **노출** (Step 2와 동일) |
| `WaitingApprovalToolbar` variant | `waiting` \| `applying` | **prop 삭제** (`FilterSeg`·`Divider`도 함께 삭제) |

**좋아진 점**

- 타일과 세그먼트를 **둘 다 두지 않는다**는 것이 이번 결정의 전부다. Step 2가 이미 타일을
  필터로 정했으므로 Step 3만 다른 조작 모델을 쓸 이유가 없다. 2→3 이동 시 같은 자리에 같은
  컨트롤이 있다.
- 세그먼트가 들고 있던 구표기가 화면에서 사라졌다(라벨은 이제 한 곳, 타일에만 있다).
- Region 필터를 Step 3에서 숨긴 근거는 v16 시안이었는데, 표는 Region 컬럼을 그대로 보여준다.
  **보이는 컬럼은 거를 수 있어야 한다** — 숨김을 유지할 이유가 없었다.

## 3. 카드 헤더 — Step 2의 스택으로 통일

**Before**: 제목 + 우측 끝 `● 반영중` 배지 → 제목 아래 한 줄에
`관리자 승인 후 … · 승인일시 2024. 01. 19. 오후 06:00 · 승인자 김보안(kim.security)` → 그 아래 초록 배너

**After**

```
[3번째 단계]                                        ← primary 태그 (INSTALL_STEPS 순서)
연동 대상 반영중  [반영중]                            ← 배지가 제목 옆, 주황 점 제거
승인이 완료되어 시스템에 반영 중입니다. Agent 설치를 …   ← 16px, 첫 문장만 파랑
                                                   ↕ 16px
승인일시                승인자                        ← 12 / 400 / #6B7280
2024. 01. 19. 오후 06:00  김보안 (kim.security)        ← 12 / 600 / #4E5968
```

| | Before | After |
|---|---|---|
| 단계 태그 | 없음 | **`3번째 단계`** (`INSTALL_STEPS` 순서에서 읽음) |
| 상태 배지 | 우측 끝, 주황 점 있음 | **제목 옆, 점 제거** |
| 초록 `StepBanner` | 있음 | **삭제** |
| 승인 메타 | 안내문 뒤에 `· 라벨 값 · 라벨 값` | **라벨 위 / 값 아래 2열** (`MetaField`) |

**좋아진 점**

- 같은 말이 **세 번** 있었다: 헤더 문장("관리자 승인 후 … 사전 작업이 자동으로 진행됩니다"),
  초록 배너("승인이 완료되어 시스템에 반영 중입니다 … 평균 5분"), 우측 가이드 패널.
  배너를 지우고 두 문장을 한 문장으로 합쳤다 — 상태(파랑) + 무슨 작업인지 + 소요시간.
- 배너가 없어지면서 카드 안의 카드가 사라지고, 타일이 헤더 바로 아래로 올라왔다.
- 메타가 안내문 꼬리에 붙어 있어 어디부터 값인지 안 보였다. 라벨/값 2열로 갈랐다.
- `MetaField`는 Step 2 카드 안에 있던 로컬 컴포넌트였다. Step 3이 같은 것을 필요로 해서
  `_components/shared/MetaField.tsx`로 옮겼다(**두 번째 사용처가 생긴 뒤에** 옮겼다).

## 4. 로딩 중 상태 태그·보조 문구 보류

**Before**: `반영중` 배지와 안내 문장이 `getApprovedIntegration` 응답 전에 먼저 그려졌다.
데이터가 도착하기 전에 헤더가 상태를 단정하고, 실패하면 그 문장 아래에 에러 행이 붙었다.

**After**: `state.status === 'ready'` 전까지 배지·문장 자리에 **스켈레톤**을 둔다.
자리를 잡아두므로 값이 들어와도 카드가 밀리지 않는다.

- 제목과 `3번째 단계` 태그는 **응답과 무관**하게 참이므로(부모가 이미 `processStatus`로 이
  카드를 골랐다) 그대로 즉시 그린다. 보류하는 것은 **응답이 결정하는 것뿐**이다.

## 5. 🐞 제외 사유 컬럼이 표를 가로 스크롤시켰다

**증상**: Azure `/2003`에서 표에 가로 스크롤바가 생기고 마지막 사유 칩
(`Legacy archive · 2024년 EOL 예정…`)이 오른쪽 끝에서 잘렸다.

**원인**: `ReasonChipInline`의 기본 요약 길이가 40자다. Step 2의 픽스처(`/1007`)는 **제외 사유가
비어 있어서** 이 컬럼 폭이 한 번도 검증된 적이 없었다. Step 3에서 사유를 별도 컬럼으로 되돌리자
6개 컬럼 + 40자 칩이 카드 폭을 넘겼다.

**수정**: `WaitingApprovalTable`에서 `summary`를 **22자로 클램프**해 넘긴다(공유 칩 컴포넌트의
기본값은 건드리지 않았다 — 다른 화면까지 번진다). 전문은 그대로 호버 팁에 있다.

> 교훈: "20건이 되면?"만이 아니라 **"값이 길면?"**도 같은 질문이다. 그리고 픽스처가 빈 값이면
> 그 컬럼은 검증된 적이 없는 것이다.
