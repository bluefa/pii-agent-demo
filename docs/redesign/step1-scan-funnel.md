# Step1 · 스캔 밴드 → 깔때기 (LIN-75)

> 작성 2026-08-03 · 대상 화면 `/target-sources/{id}` 1단계 "연동 대상 DB 선택"
> 적용 컴포넌트: `ScanStrip`(밴드 + `FunnelCell`) / `CandidateResourceSection`(카운트 공급)
> 재사용: `useApprovalTableState`의 `ApprovalFilter`·`countsByFilter` (신규 상태 없음)
> 선행 근거: `docs/redesign/admin-scan-tab.md` §9 — Admin 스캔 탭에서 확정된 표시 문법
> 진행 방식: 대안 5안 시안 비교 → D안 선택 → 라이브 리뷰 2라운드

Admin 스캔 탭의 문법을 Step1로 가져오되, **카드가 아니라 문법만** 가져왔다.
이 문서는 확정된 결정과 다음 화면에 들고 갈 교훈만 남긴다.

---

## 1. 왜 Admin 카드를 그대로 옮기지 않았나

| | Admin 스캔 탭 | Step1 |
|---|---|---|
| 사용자 질문 | "스캔이 제대로 돌았나" | "어떤 DB를 연동할까" |
| 주인공 | 스캔 잡 | 후보 표 |
| 스캔의 역할 | 관찰 대상 | 표의 **공급원** |
| primary CTA | 스캔 실행 | 승인 요청 (하단 CardActionBar) |

`RecentScanCard`를 통째로 옮기면 한 카드에 primary CTA가 둘(스캔 실행·승인 요청)이
되어 계층이 뒤집힌다. 가져온 것은 문법 여섯 개다 — 숫자는 정렬, 증감은 정직하게,
컨테이너 높이는 콘텐츠 수가 아니라 레이아웃, 진행바는 진행 중일 때만, 식별자는 저장값,
카드=요약/모달=정밀.

## 2. 메타 문자열 → 깔때기 4칸

| Before | After | 고쳐진 것 |
|---|---|---|
| `14:03 · 12초 소요 · 107,873개 발견 · 신규 3` 한 줄 | 정렬된 4칸 `스캔 발견 → 연동 가능 DB → 선택함 → 제외함` | 가운뎃점으로 이어붙인 숫자는 서로 비교가 안 된다 — Admin §1이 고친 "칩 안 숫자"의 문자열 버전 |
| `107,873개 발견` 뒤에 곧바로 DB 12행 | 발견(전체 리소스) → 연동 가능(표) 단계로 배치 | 격차가 사고가 아니라 **설계된 좁혀짐**으로 읽힌다 |
| 제외 사유 미입력은 승인 버튼 툴팁에만 | `제외함` 칸에 `사유 N건 미입력` | 진행을 막는 조건이 눈에 보이는 자리로 |

**교훈: Step1 고유의 질문은 "왜 내가 찾던 DB가 안 보이지"다.** Admin에는 이 질문이
없어서, Admin 카드를 아무리 잘 이식해도 이건 풀리지 않는다. 화면을 옮길 땐 문법을
옮기고, 질문은 그 화면에서 다시 찾는다.

## 3. 숫자가 곧 조작

- `선택함`·`제외함`은 실제 `<button>` + `aria-pressed`. 누르면 표가 걸러지고,
  켜진 칸을 다시 누르면 전체로 돌아온다(유일한 해제 경로).
- 필터는 **신규 상태가 아니다** — `useApprovalTableState`에 이미 있던 `ApprovalFilter`가
  Step1 툴바에서만 노출되지 않고 있었다. 깔때기가 그 컨트롤이 됐을 뿐이라 중복이 없다.
- `스캔 발견`·`연동 가능 DB`는 평문 `<div>`. 필터가 없는 칸이 버튼처럼 보이면 안 된다.
- 필터 변경은 다른 뷰 변경 핸들러와 똑같이 행 앵커 UI(확장 패널·제외 팝오버)를 닫고,
  재스캔 때 `all`로 초기화된다. (죽은 앵커 방지 — 기존 규칙에 편입)

## 4. 없는 결과를 있는 것처럼 그리지 않는다

라이브 리뷰에서 잡힌 결함. 스캔 기록이 없을 때 `발견 —` 옆에 나머지 세 칸이 숫자를
계속 보고해서, **부재가 결과처럼 읽히고** 정작 그 화면의 유일한 사실
("아직 스캔한 적이 없어요")이 셀 아래로 밀렸다.

- `ScanStrip`이 규칙을 소유한다: `showFunnel = funnel != null && job != null`.
  스캔이 없으면 밴드는 한 줄로 접히고, 그 한 줄이 곧 안내 문장 + `스캔 시작` CTA다.
- 호출부는 숫자만 공급하고, "이 깔때기가 정직한가"는 렌더하는 쪽이 판단한다 — 판정이
  한 군데에만 있게.
- 종료됐지만 실패한 스캔은 깔때기를 유지한다. 아래 표는 직전 스캔 결과이고, 이번 판의
  빈 결과는 `0`이 아니라 `—`다. (`0`은 "0개 발견"이라는 거짓말)

**교훈: 파생 화면은 원본 데이터의 부재를 표현할 수 있어야 한다.** 값이 없을 때
0으로 떨어지는 집계는 "없음"과 "0"을 같은 화면으로 만든다.

## 5. 같은 숫자를 두 번 세지 않는다

깔때기가 발견 수·신규를 가져가면 아래 메타 줄에서는 빠진다(시각·소요만 남음).
`newCount`도 props 두 곳에 두지 않고 기존 최상위 prop 하나를 셀이 읽는다.

## 6. 타이포 — 굵기가 아니라 크기·색이 위계를 진다

라이브 리뷰 확정: 22px 값은 `extrabold` → **`medium`**(Admin 리소스 타일과 같은 weight),
네 칸 모두 가운데 정렬. 칸 폭이 같으므로 가운데 정렬로도 숫자는 한 세로줄에 선다.
크기(22px)와 색(브랜드색은 `연동 가능 DB`만)이 이미 위계를 지고 있어서 굵기는 노이즈였다.

## 7. 남긴 것 (근거 있는 보류)

- **`스캔 발견`의 증감(+187)** — 직전 성공 잡의 count map이 필요해 Step1 진입마다
  스캔 이력 fetch가 한 번 더 붙는다. 네 숫자 중 행동 가치가 가장 낮은 값의 증감이라
  요청 한 번을 벌 만한지 확인 후 넣기로 보류. 넣을 땐 **직전 성공 스냅샷에서만** 파생
  (`rows`에서 파생하면 페이지네이션이 증감을 흔든다 — Admin §6 재현).
- **하단 CardActionBar의 `총 N건 · N건 선택됨`** — 깔때기와 숫자가 겹치지만 액션바는
  sticky라 표가 길 때 제 역할을 한다(제출 가능 여부). 역할이 달라 유지.

## 8. 다음 화면에 들고 갈 것

1. 화면을 옮길 땐 문법을 옮기고, 그 화면의 질문은 다시 찾는다.
2. 집계 화면은 원본의 **부재**를 0이 아닌 방식으로 표현할 수 있어야 한다.
3. "이 표시가 정직한가"의 판정은 렌더하는 컴포넌트 하나가 소유한다.
4. 새 상호작용을 붙이기 전에 기존 상태 훅에 이미 있는지 본다(여기선 `ApprovalFilter`).
5. 위계는 크기·색으로 먼저, 굵기는 마지막에.

## 9. 개정 (2026-08-03, 운영 피드백 2차) — 깔때기 4칸 → 3칸

`스캔 발견`(≈9만)을 **셀에서도 메타 줄에서도 삭제**했다. 밴드는
`연동 가능 DB · 선택함 · 제외함` 3칸이고 `선택함 + 제외함 = 연동 가능 DB`다.

**왜 뒤집혔나.** §2는 "발견 → 연동 가능"을 나란히 두면 격차가 *설계된 좁혀짐*으로
읽힌다고 봤다. 실제 화면에서는 반대로 읽혔다 — 네 칸 중 뒤 세 칸만 합이 맞고
첫 칸은 **단위가 다르다**(전체 리소스 vs 후보 DB). 같은 행·같은 크기·같은 정렬은
"비교하라"는 지시라서, 사용자는 `87,914 : 10`을 비교하고 답이 없는 질문
("왜 9만 개 중 10개뿐이지")을 얻었다. 조회 규모는 **스캔 잡의 사실**이지
1단계의 결정 입력이 아니다 — 그 숫자로 바뀌는 사용자 행동이 없다.

**교훈: 한 줄에 나란히 선 숫자는 같은 단위여야 한다.** 단위가 다른 값을 나란히
두면서 캡션으로 설명하려 하면, 캡션은 읽히지 않고 비교만 남는다. 설명이 필요한
배치는 배치가 틀린 것이다. (§7 보류였던 `스캔 발견` 증감은 칸 자체가 사라져 함께 소멸.)

**미해결.** "왜 내가 찾던 DB가 안 보이지"는 이제 밴드가 답하지 않는다. 표의
`설치 불가` 행(`integrationCategory === 'INSTALL_INELIGIBLE'`)이 유일한 답이고,
지금은 `제외함`에 사용자 제외와 함께 뭉쳐 있다. 갈라 세우는 안(4번째 칸
`설치 불가`)은 검토 후 보류 — 필요해지면 추가 fetch 없이 `candidates`에서 센다.

### 9-1. 함께 뒤집은 결정 — Resource ID 축약 방향

`ResourceIdCell` 이 좌측 절단(`direction: rtl`, 꼬리를 남김)에서 **우측 절단**
(`Prefix…`)으로 바뀌었다. v16 정렬 리뷰(`docs/v16-alignment/03-review-r1-findings.md`
azure-s2)는 정반대를 결함으로 적었다 — "우측 절단이면 모든 행이 동일한 접두어만
보인다". 그때 근거는 여전히 사실이지만, **행을 식별하는 책임이 Resource Name 열에
있다**는 점이 결정을 바꿨다: 축약 문법이 한 표 안에서 두 개(이름은 `Prefix…`,
id 는 `…tail`)일 이유가 없고, 전체 값은 툴팁과 복사 버튼이 이미 보장한다.

소비처 6곳 중 이름 열이 없는 곳은 `ConnectionTestCard` 의 접힌 Athena/리전 행뿐이고,
그 값은 짧은 그룹 키라 잘리지 않는다. **v16 감사에서 azure-s2 를 재발행하지 말 것** —
되돌리려면 이 항목부터 뒤집어야 한다.

## 10. 개정 (2026-08-23) — 결과 조회는 성공한 스캔 뒤에만

**게이트.** `useCandidateResources` 가 리소스 목록을 조회하기 전에 최신 스캔 잡을
읽고, `hasScanResults`(= `SUCCESS` 이고 집계 꼬리가 아님)일 때만 조회한다. 아니면
빈 목록으로 앉고 화면은 스캔 잡이 말하는 프레임(온보딩 히어로 · 진행 중 · 실패)을
그대로 쓴다.

**왜.** 조회 응답(`CloudResourceResponse`)에는 그 행들이 어느 스캔에서 나왔는지
말해 주는 칸이 없다 — 계약에 `scan_version` 도 `scanned_at` 도 없다. 그래서 "이 표를
그려도 되는가"는 표가 답할 수 없고 스캔 잡만 답할 수 있다. 게이트가 없을 때의 실제
증상 둘:

1. **스캔한 적 없는 화면에 표가 선다.** 목은 스캔 이력과 무관하게 시드 리소스를
   돌려주므로 데모에서 늘 이랬다(`lib/bff/mock/confirm.ts` `getResources`).
2. **조회 에러가 스캔 상태를 이긴다.** `selectPhase` 는 `fetchError` 를
   `scanning`·`empty` 보다 먼저 판정하고, 그 프레임에는 스트립도 히어로도 없다 —
   무스캔 타겟소스가 404 를 받으면 스캔 시작 입구가 없는 막다른 화면이 됐다.
   **이건 잠재 결함이 아니라 실제로 나던 결함이다**: 상류는 스캔 결과가 없는
   타겟소스에 404 로 답한다(오너 확인 2026-08-23). 목이 시드 리소스를 무조건
   돌려주고 있어서 데모에서만 안 보였을 뿐이다.

**판정은 닫힌 쪽으로 — 단, 실패를 부재로 말하지 않는다.** 잡을 못 읽으면(네트워크·5xx)
SUCCESS 를 *확인하지 못한* 것이므로 조회하지 않는다. 그렇다고 "스캔한 적 없음"으로
그리면 안 된다: `fetchLatestScan` 은 404 만 `null` 로 접고 나머지는 던지는데, 그 던짐을
삼키면 결과 40건을 가진 타겟소스가 잡 엔드포인트 장애 동안 온보딩 히어로를 세우고 그
화면의 CTA 가 **새 스캔**이 된다(리뷰 지적, 반영). 던지면 `fetchError` 프레임이 서고 표는
여전히 안 열린다 — 닫힌 판정은 그대로, 문장만 정직해진다.

같은 이유로 `showStrip` 은 `fetchError` 에서 **끝난 잡을 실제로 읽었을 때만** 스트립을
세운다. 잡이 `null` 인 채로 온 실패 화면에 무기록 폴백("아직 스캔한 적이 없어요")을 띄우면,
방금 지운 거짓말을 에러 박스 옆에 다시 세우는 꼴이다.

**게이트는 최신 잡의 규칙이다 — 상류보다 좁다.** 상류는 "성공이 한 번이라도 있었나"로
답하고(아래 목도 그렇게 만들었다) 게이트는 최신 잡만 본다. FAIL·TIMEOUT 은 차이가 화면에
안 나오고(`selectPhase` 가 그 프레임을 먼저 가져간다), 남는 갈래는 CANCELED 하나인데 앱에도
목에도 취소 경로가 없다. 넓히려면 이력 조회가 한 번 더 붙고 그 값이 CANCELED 에서만 생기므로
달지 않았다 — 취소가 실제로 생기면 그때가 이 결정의 만료일이다.

**비용.** 진입당 스캔 잡 읽기 1회가 늘었다. 같은 잡을 `ScanController` 도 폴링하지만
그 값은 렌더 트리 안에서만 살아 있어 이 훅이 볼 수 없다 — 조회를 여는 판정을 조회
바로 옆에 두는 값으로 요청 하나를 지불했다.

**목도 그 사실을 만든다.** `mockConfirm.getResources` 가 성공한 스캔 이력이 하나도
없으면 404 로 답하고, **리소스를 들고 태어난 시드 프로젝트에는 그것을 발견한 스캔 이력도
같이 깔린다**(`lib/mock-store.ts` `buildSeedScanHistory`). 둘 중 하나만 하면 목이 제
픽스처와 모순된다: 이력이 빈 채로 404 만 켜면 큐레이션된 1단계 화면 전부(Athena 그룹·RDS
클러스터 선택·연동 불가 행·중국 리전)가 스캔부터 돌려야 닿는 곳이 되고, 그 스캔이 픽스처
위에 무작위 리소스를 얹어 화면이 매번 달라진다. 스캔한 적 없는 상태는 리소스 없이 태어난
타겟소스(1002)가 그대로 보여준다. 목이 시드 리소스를 무조건 돌려주는 동안에는 게이트가 무엇을
막는지 화면으로 확인할 수 없었다 — 데모에서 스캔 없이 표가 서던 그 화면이다. 마지막
스캔이 실패여도 **직전 성공의 결과는 남아 있다**(상류의 보관 단위가 스캔 결과이지 최신
잡이 아니므로): 판정은 "SUCCESS 이력이 한 번이라도 있는가"다.

**게이트를 통과한 뒤의 404 는 재스캔으로만 풀린다.** 조회가 성공한 스캔 뒤에만 열리므로
`fetchError` 에 닿았다는 건 SUCCESS 잡은 있는데 결과가 사라졌다는 뜻이다(보관은 최근 10개
버전뿐 — §9 페이지 크기의 그 정책). "다시 시도"는 같은 404 를 다시 받는다. 그래서
`showStrip` 이 `fetchError` 를 포함한다 — 그 화면에서 실제로 할 수 있는 일은 재스캔뿐이고,
스트립이 그 유일한 입구다.

### 10-1. 함께 손본 표 — 제외 사유 열의 폭

자동 레이아웃에서 열 폭은 셀의 max-content 다. 제외 사유 칩은 40자까지 인라인으로
찍히므로(`ReasonChipInline`) 사유 한 줄이 **Resource ID 보다 넓은 칸**을 가져갔다
(실측 253px vs 196px). 행을 식별하는 것은 이름과 id 이고 사유 전문은 칩의 팁이 갖는다.

- 칩을 `max-w-[150px]`(`REASON_CLAMP`) 로 클램프 → 사유 열 253 → 186px (실측, 1002 픽스처)
- 그 폭을 Resource ID 로: `maxWidthClass` 160 → 220px → 열 196 → 261px
- Resource Name 클램프는 **200px 유지**. 280 으로 올려 봤더니 ARN·긴 이름이 모인
  AWS 표(1006)에서 표가 컨테이너를 넘어 가로 스크롤이 생겼다(1071 > 990) — 이 표의
  폭 예산은 이미 꽉 차 있어서, 한 열에 주는 픽셀은 다른 열에서 빼 온 것이다.
- 헤더의 `w-[160px]` 는 **상한이 아니라 하한**이다. 열 폭은 셀의 max-content 라 상한은
  칩 클램프가 정하고(186), 이 값은 사유가 하나도 없는 표에서 열이 「사유 입력」 링크
  폭까지 쪼그라들지 않게 잡는다. 둘이 열을 160~186 사이에 묶는다.
- 두 화면에서 가로 스크롤 없음 실측: 1002(사유 칩 있음) 990=990, 1006(ARN 다수) 990=990.

**그룹 행의 집계 줄 삭제.** Athena 그룹 머리의 `데이터베이스 · 대상 N · 제외 N`
(`ResourceGroupCount`)을 1단계 표에서 내렸다(오너). 같은 숫자를 위의 깔때기와 하단
액션바가 이미 말한다. 2·3단계 표(`WaitingApprovalTable`)는 깔때기가 없으므로 유지.

- **감수한 것**: 그룹은 기본 접힘이라, 리전이 둘 이상이면 접힌 그룹은 제 구성을 말하지
  않는다(깔때기·액션바의 숫자는 목록 전체 합이지 그룹별이 아니다). `ResourceGroupRow` 의
  주석이 갖고 있던 "접어도 몇 건인지는 숨기지 않는다"는 불변식은 이제 `inlineMeta` 를
  넘기는 호출부(2·3단계)에만 해당한다 — 주석도 그렇게 고쳤다.
- **함께 고친 것**: 셋째 줄이 빠지면서 셰브론이 12px 위로 떠 태그에 붙어 보였다(실측
  chevMid 1326 vs regionMid 1337). `toggle` 은 스택의 **박스** 가운데에 걸리는데 세 줄일
  때는 그 가운데가 곧 이름 줄이었기 때문이다. `inlineMeta` 가 없을 때만 반 줄(12px) 내려
  이름 줄에 다시 앉혔다 — 실측 delta 0. 움직인 것은 셰브론이지 이웃 열이 아니다.
