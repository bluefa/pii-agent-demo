> 2026-07-31 · 화면 `/pass/target-sources/1007` (AWS Step 2, mock BFF)
> 결과 정리: `docs/redesign/step2-approval-waiting.md`
> 이 문서는 **무엇을 어떤 순서로 요청했고, 그 요청이 어떤 판단을 거쳐 무엇이 됐는지**의 기록이다.
> 다음 Step을 같은 방식으로 진행할 때 참고용.

## 진행 방식

dev 서버를 띄워 **실제 화면을 보면서** 한 번에 한 가지씩 요청 → 즉시 반영 → 다시 보고 다음 요청.
스펙 문서를 먼저 쓰고 한 번에 구현하는 방식이 아니었다. 요청 단위가 작아서 되돌리는 비용도 작았고,
실제로 한 건(표 가운데 정렬)은 보고 나서 바로 되돌렸다.

각 변경마다 `npx eslint` + `npx vitest run app/target-sources/` (260 tests)를 돌렸다.
문구·라벨을 바꿀 때마다 테스트가 먼저 깨져서, 어떤 텍스트가 계약처럼 쓰이고 있는지 매번 드러났다.

## 이 세션에서 반복된 5가지 요청 유형

1. **중복 제거** — "이거 꼭 있어야 하나?" (퍼센티지, 색 스와치, 세그먼트, 건수, 필터 초기화, 점)
   → 6건 중 6건 삭제. 화면에 있는 것을 지우는 요청이 가장 많았고 전부 옳았다.
2. **계층 분리** — "계층이 안 잡힌다 / 계층을 다운시키자"
   → 답은 항상 "축을 늘리지 말고 이미 있는 축(굵기·색·크기·들여쓰기)을 벌려라"였다.
3. **이름 검토** — "이 이름이 적절한지 검토해봐"
   → 헤더는 질문, 셀은 답. 컬럼명 안에 셀 값이 들어가 있으면 잘못된 이름이다.
4. **신호 교정** — "실행하면 안 되는 느낌 말고", "왜 이걸 강조하지?"
   → 색·배지·태그는 전부 신호다. 신호와 실제 위험도/중요도가 어긋나면 사용자가 잘못 배운다.
5. **파손 조건 질문** — "20개가 되면 깨지지 않아?"
   → 목 데이터 3건으로는 안 보이는 문제. 스크롤·상한·wrap을 먼저 정하게 만든 질문이었다.
