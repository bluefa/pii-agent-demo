## 이 세션에서 반복된 5가지 요청 유형

1. **중복 제거** — "이거 꼭 있어야 하나?" (퍼센티지, 색 스와치, 세그먼트, 건수, 필터 초기화, 점)
   → 6건 중 6건 삭제. 화면에 있는 것을 지우는 요청이 가장 많았고 전부 옳았다.
2. **계층 분리** — "계층이 안 잡힌다 / 계층을 다운시키자"
   → 답은 항상 "축을 늘리지 말고 이미 있는 축(굵기·색·크기·들여쓰기)을 벌려라"였다.
3. **이름 검토** — "이 이름이 적절한지 검토해봐"
   → 헤더는 질문, 셀은 답. 컬럼명 안에 셀 값이 들어가 있으면 잘못된 이름이다.
4. **신호 교정** — "실행하면 안 되는 느낌 말고", "왜 이걸 강조하지?"
   → 색·배지·태그는 전부 신호다. 신호와 실제 위험도/중요도가 어긋나면 사용자가 잘못 배운다.
5. **파손 조건 질문** — "20개가 되면 깨지지 않아?"
   → 목 데이터 3건으로는 안 보이는 문제. 스크롤·상한·wrap을 먼저 정하게 만든 질문이었다.

## 세션 2의 교훈

1. **상태 분기는 문법 재사용이다.** "갑자기 생기는 요소" 불만의 원인은 rejected가 pending과 다른
   구조를 쓰는 것이었다. 상태 전환은 구조가 아니라 내용을 바꿔야 한다.
2. **흐림은 상대값.** 이웃이 15.9:1이면 4.63:1로도 체감 3배 감광 — 법칙(4.5:1)을 깨지 않고 원하는
   인상을 얻는다. 3:1은 대형 텍스트·비텍스트 전용이고, 읽어야 하는 콘텐츠에 "비활성 예외"는 없다.
3. **색이 다른 이유를 물으면 위계로 답하라.** 접근성 법칙은 하한이지 설계 이유가 아니다.
   실측표(4.83/9.71/16.71)가 논쟁을 끝낸다.
4. **거짓 경고는 UX 부채.** "보존되지 않습니다"류 손실 경고는 사실 검증에서 두 번 깨졌다.
   모달 문구는 시스템 동작의 계약 — 이력이 남으면 남는다고 쓰거나 아예 쓰지 않는다.
5. **강조 토큰은 짧게.** `1단계`(3글자)는 인라인 강조가 안전하고, 긴 화면 이름은 조사가 경계를
   부순다. 문장은 "확인을 누르면 …해요"로 버튼과 결과를 직결한다.
6. **비교 페이지가 결정을 빠르게 한다.** 반려 사유(5안)·제외행(6안) 모두 실제 스타일로 나란히
   보여주자 한 번에 골랐다. 제안은 글이 아니라 렌더로.
7. **시도-롤백 비용을 낮게 유지하라.** 선택행 bold(E안)는 승인받고 적용했지만 화면을 보고 즉시
   철회됐다. 작은 단위라 되돌리기가 공짜였다.
8. **`cn`은 plain join.** 색 클래스 2개가 겹치면 승자는 스타일시트 순서다. 공용 셀 컴포넌트의
   색 주입은 "전달 시 대체" 계약으로 만들어야 한다 (`ResourceIdCell.textClassName`).
9. **목 스토어는 리뷰어도 조작 중이다.** 라이브 리뷰에서 confirm 클릭은 mock 상태를 진짜로 바꾼다.
   모달은 캡처 즉시 Escape, 상태가 꼬이면 dev 서버 재시작으로 재시드.
10. **공용 컴포넌트 재설계는 양쪽에 동시 상륙한다.** "step3 테이블을 step2에"의 실체는 새 디자인
    포팅이 아니라 **베이스 동기화**였다. 미커밋 작업은 WIP 커밋 → 새 브랜치 → cherry-pick(3-way)이
    안전했다.
