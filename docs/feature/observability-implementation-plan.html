01확정 결정

#결정이유
①FE 로그는 BFF로 전송, BFF가 자체 DB에 저장 — stdout→Cloud Logging 폐기 FE가 서로 다른 GCP 프로젝트로 최소 2회 마이그레이션 예정. BFF는 이사하지 않는 고정점 — 저장소·집계·히스토리가 FE 이사와 무관
②인증 전제 + 로그인 필수 로그인 없이는 페이지 접근 불가. userId는 서버가 세션에서 resolve(클라이언트 헤더 신뢰 금지)
③sessionId 완전 제거 로그인 전 구간이 존재하지 않아 메울 공백이 0. userId가 상위 호환, SSR 예외 처리도 제거
④세션 리플레이 안 함 "화면 재현" 불필요 — 행동 흐름(무엇을 했는지)만 알면 충분
⑤Grafana는 결정 보류 "push 알림이 필요한가"부터 결정. 후보 구성은 §05에 보존

결정 ①의 트레이드오프 (인지하고 수용)

stdout 무부하 → 네트워크 전송 부하(배치·비동기로 완화), best-effort 유실 허용, Error Reporting 자동 그룹핑·로그 기반 metric 상실 → 그룹핑·집계·알림을 BFF DB 쿼리로 직접 구성.

03작업 목록 — Phase 0~6

Phase 0 PR #558 머지 전제 조건리뷰만

수집 계층 전체(바운더리·로거·수신 라우트·헤더 3종·링버퍼·PII 가드)가 이 PR에 있다. 저장소가 바뀌어도 이 계층은 전부 재사용 — 교체 대상은 log.ts의 출구뿐.

완료 기준 — main 머지, 전체 테스트 green.

Phase 1 BFF 협의 외부 의존 — 지금 시작
#작업상세
1-1ingest API 계약엔드포인트·배치 payload 스키마·서버 간 인증·크기 캡·실패 시 FE 드랍 정책
1-2이벤트 스키마·DB 필드공통 필드 확정. errorMessage 컬럼 없음. errorName/fingerprint 포함 여부는 열린 결정
1-3보존·삭제 정책보존 기간(예: 상세 90일+집계 롤업)·삭제 주기·용량 상한 — "많아지면 삭제"의 구체 기준
1-4조회 API 계약Admin 기능 목록(§04)이 요구사항 — 최근 에러·추이·top-N·userId/타깃/requestId 필터·403 목록

완료 기준 — 계약·스키마·보존 정책 합의 문서화. Phase 2·4의 입력.

Phase 2 FE 전송 교체 + 필드 정책 FE 코드 본체 ①전제: 0·1
#작업상세
2-1surface 필드surfaceOf() — pageTemplate prefix로 4값 파생, 모든 이벤트에 추가
2-2log.ts 출구 교체버퍼→배치(N건 또는 T초) 비동기 POST→BFF ingest. 실패/초과 시 드랍+유실 카운터, 종료 시 flush. 전송 실패가 요청을 막지 않음
2-3진단 로그 분리새니타이즈 스택 등 상세는 stdout 진단 로그로만 — BFF payload에서 제외, errorMessage 원문은 어디에도 없음
2-4브라우저 리포트 정합수신 라우트도 같은 출구(log.ts→BFF)로. 방어(allowlist·캡·rate limit)는 그대로
2-5sessionId 흔적 제거X-Session-Id 관련 코드·계획 흔적 grep 0건 확인

완료 기준 — 테스트 이벤트가 FE→BFF→DB 레코드로 저장, DB에 errorMessage 없음.

Phase 3 인증 연동 인증 도입(~1개월) 후
#작업상세
3-1userId·role resolvewithV1이 세션에서 읽어 모든 이벤트에 심음 — 클라이언트 헤더 채택 금지
3-2인가 거부 403 — API인가 검사 실패 시 {userId, role, 경로, 403} WARN 이벤트
3-3인가 거부 — 페이지middleware/SSR 가드의 거부는 withV1 밖 — 별도 구현 필수 (자동 아님)
3-4SSR 화면 식별SSR엔 X-Client-Page 없음 — 서버가 렌더 경로를 직접 심는 구현 (방법은 열린 항목)

완료 기준 — 모든 이벤트에 userId·role, 403이 API·페이지 양쪽에서 기록.

Phase 4 In-app Admin 대시보드 FE 코드 본체 ②전제: 1·2 (일부는 3)

기능 명세는 §04. 구성: FE 프록시 라우트(운영자 role 검사·24h 기본 창) → 관제 화면(A1~A3) → 드릴다운(B4~B5) → 엔티티 축(C6~C7) → 보안·감사(D8~D9). 기존 admin 패턴(theme.ts 토큰·한국어 UI) 준수.

완료 기준 — "최근 에러 → 상세 → 해당 고객/타깃 이력 → 403 시도"까지 Admin 안에서 도달.

Phase 5 page_view 이벤트 전제: 2 · 소규모

라우트 전환 감지(usePathname) → {event: page_view, pageTemplate, surface} 전송. 사람 묶기는 userId(서버가 심음) — sessionId 없음. 이벤트 종류별 rate cap 분리 재점검.

Phase 6 Grafana 보류 — 도입 결정 후

판단 기준: "사람이 들어가 보기 전에 시스템이 먼저 알려야 하는가" (push 알림 필요성). 필요 시: BFF DB 읽기 전용 계정 → Grafana SQL 데이터소스(로그 기반 metric 파이프라인 불필요) → 후보 패널·알림(§05) → Slack 수신 확인. 고카디널리티(고객/타깃별) 패널 금지.

의존 관계

Phase 0 (PR #558 머지)
  └─→ Phase 2 (전송 교체·필드 정책) ─→ Phase 4 (Admin) ─→ Phase 5 (page_view)
Phase 1 (BFF 협의) ─→ Phase 2·4        ← 코드와 무관, 지금 바로 시작
Phase 3 (인증 연동) ─→ Phase 4의 userId·403 축
Phase 6 (Grafana)   ← 도입 결정 후, 언제든

04In-app Admin 제공 기능 (확정)

#그룹기능내용
A1관제최근 에러 목록시각·source(browser/server)·surface·pageTemplate·code·status·requestId
A2관제에러 추이 24h/7dbrowser/server 분리, surface별 스택
A3관제API 사용량 top-NclientAction별 호출 수·p95·실패율 — 폴링 분리 표시
B4드릴다운에러 상세breadcrumbs(직전 API 10건)·requestId 체인·"에러 난 화면으로 이동" 링크
B5드릴다운requestId 검색단일 요청의 전체 흐름 — "FE 에러인데 BFF는 200" 판별
C6엔티티고객별 활동 타임라인"이 고객이 최근 뭘 했나" — 방문·API·에러 시간순
C7엔티티타깃소스별 이력 + 현재 상태이력(로그) + 도메인 API의 현재 process status 병합 — MVP 포함 여부는 열린 항목
D8보안인가 거부(403) 시도 목록userId·role·시도 경로·시각 — 권한 없는 접근 시도
D9감사CTA(쓰기) 실패 추적method(POST/PUT/DELETE)+clientAction+status — "쓰기가 진짜 됐나" (전용 뷰 vs 필터: 열린 항목)
E10운영접근 통제·조회 창운영자 role만 · 기본 24h 창 · 자동 갱신 여부는 열린 항목(관제탑 vs 조사실)

05Grafana 후보 (보류)

#종류후보비고
G1패널surface별 에러율 추이고객 대면(target-detail)과 내부(admin) 분리
G2패널에러 급증 감지 + 배포 마커"배포 직후 터졌나" 즉답
G3패널API 호출량·p95clientAction별 — 저카디널리티만
G4패널CTA(쓰기) 실패율method+status 집계
G5패널ingest 유실 카운터관측 파이프 자체의 건강
G6알림target-detail 에러율 임계 → Slack민감 임계 — 고객이 작업 중 실패
G7알림server ERROR 급증 → Slack느슨 임계
G8알림403 시도 급증 → Slack보안 신호

금지: 고객별/타깃별 드릴다운 패널(고카디널리티) — Admin의 몫. Admin = pull(들어가서 팜) · Grafana+Slack = push(문제가 사람을 부름).

06하지 않는 것 · 열린 항목

명시적 스코프 아웃

  • 세션 리플레이·히트맵 — 행동 흐름 재구성으로 충분 (결정 ④)
  • sessionId — 익명 구간이 없음, userId가 상위 호환 (결정 ③)
  • errorMessage 저장 — 자유 텍스트 PII 위험, code/status만 구조화 저장
  • 전용 수집 서버(Sentry/Bugsink 등) — 보류, 승격 경로만 보존
  • OpenTelemetry 분산 트레이싱 — requestId 상관관계가 경량 대체
  • 클라이언트가 보내는 userId 헤더 — 위조 가능, 영구 채택 금지

열린 항목 (결정 필요)

  • Admin의 성격 — 관제탑(자동 갱신) vs 조사실(수동 조회)
  • CTA 실패 — 전용 뷰 vs 필터 축
  • 로그+도메인 상태 병합(C7)을 MVP에 넣을지
  • errorName/fingerprint 저장 권고안 채택 여부
  • BFF DB 스키마 상세 — 필드·보존 기간·삭제 정책
  • FE→BFF 전송 방식 — 배치 크기/주기·유실 허용 범위
  • SSR 화면 식별 구현 방법
  • Grafana/알림 도구 도입 자체
