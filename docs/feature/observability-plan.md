# FE 관측성 계획 — 읽기용 정리본

> 이 문서는 "무엇을, 왜, 어떻게"를 처음부터 읽을 수 있게 정리한 것이다.
> 결정 과정의 Q&A·리서치 전문은 `observability-via-bff.md`(아키텍처)와
> `error-boundary-and-error-tracking-plan.md`(초기 계획 + 트래커 리서치)에 있다.

---

## 1. 한 줄 요약

**에러와 API 사용 이력을 "구조화 로그"로 남기고, 이미 있는 인프라(Stackdriver → Grafana → Slack)가
저장·대시보드·알림을 담당한다.** 새 수집 서버는 만들지 않는다.

---

## 2. 어떤 문제를 푸는가

운영 배포 전의 상태는 이랬다.

| 문제 | 지금까지 | 배포 후 생길 일 |
|---|---|---|
| 화면에서 에러가 나면 | 에러 바운더리가 앱 전체에 1개뿐 | 사용자는 **흰 화면**을 보고 이탈 |
| 에러가 났다는 사실을 | 아무도 기록하지 않음 | 사용자가 신고하기 전까지 **우리는 모름** |
| 어떤 API가 쓰이는지 | 기록 없음 | 장애 분석·사용 분석 불가 |

그리고 제약이 있다.

- **폐쇄망**: FE 서버의 아웃바운드는 BFF·OAuth·인가 서버뿐. Slack도, 외부 SaaS도 직접 못 부른다.
- **FE는 얇게**: FE 서버에 저장소·집계·알림 같은 무거운 역할을 두지 않는다.
- **사용자가 많을 수 있다**: 로그를 눈으로 뒤지는 방식으로는 관리가 안 된다 → 대시보드가 필요하다.

---

## 3. 왜 "로그 기반"인가

처음엔 Sentry SDK + 전용 수집 서버(Bugsink)를 검토했고 리서치·외부 검증까지 마쳤다.
그런데 확인 과정에서 두 가지 사실이 드러났다.

1. FE 컨테이너의 stdout은 **이미 Stackdriver(Cloud Logging)가 수집**하고 있다.
2. **Grafana와 Slack 알림도 이미 가능**하다 (GCP metric 기반).

즉 "저장·대시보드·알림"이 전부 이미 존재한다. 없는 것은 **에러를 그 파이프에 넣는 부분**뿐이었다.
그래서 전용 수집 서버(컨테이너 2대 + 운영 부담)를 세우는 대신, 에러를 로그로 취급하기로 했다.

**"로그는 구조화하기 어렵지 않나?"** — 어려운 것은 자유 텍스트를 나중에 파싱하는 방식이다.
이 설계는 반대로 **쓰는 순간에 구조화**한다. 코드의 한 함수(`app/api/_lib/log.ts`)만이
고정된 필드의 JSON 한 줄을 찍고, Cloud Logging은 이것을 필드 단위로 인식한다.
`clientPage="/services"인 로그만 보여줘` 같은 검색이 파싱 없이 바로 된다.

**버린 것과 그 대가** — Sentry를 안 쓰므로 ① 브라우저 압축 코드의 스택을 원본 코드 위치로
자동 변환(소스맵 심볼리케이션)해주는 기능과 ② 이슈 할당/해결/회귀 감지 같은 관리 기능이 없다.
대신 에러 리포트에 "어느 페이지, 직전 API 호출 10건"이 붙어 있어 원인 특정은 대부분 가능하다.
이 갭이 실제로 아프면 그때 Bugsink를 승격한다(검증된 도입 절차가 문서에 보존돼 있다).

## 4. 에러가 나면 무슨 일이 벌어지나 (시나리오)

### 시나리오 A — 사용자 화면에서 렌더 에러

1. React가 에러를 던진다.
2. **에러 바운더리**가 받는다 — 사용자는 흰 화면 대신 "문제가 발생했습니다 + 다시 시도" 화면을 본다.
   (세그먼트 → 루트 → 최후의 `global-error` 3단 방어. raw 에러 메시지는 노출하지 않는다)
3. 바운더리가 동시에 에러 리포트를 FE 서버의 수신 API(`POST .../observability/client-errors`)로 보낸다.
   리포트에는 **어느 페이지였는지 + 직전 API 호출 10건**이 함께 담긴다.
4. 수신 API는 내용을 엄격히 검증(허용 필드만, 크기 제한, 분당 상한)한 뒤 **ERROR 로그 한 줄**로 찍는다.
5. 로그는 플랫폼이 수집해 Cloud Logging에 쌓이고 → Error Reporting이 같은 에러끼리 묶고 → Grafana 알림이 울린다.

### 시나리오 B — API 호출이 실패

1. 브라우저의 모든 API 호출은 단일 래퍼(`fetchJson`)를 지나며 **요청 ID + 어느 화면 + 무슨 행동** 헤더가 붙는다.
2. FE 서버의 라우트가 처리하다 실패하면 — 예외든 BFF의 5xx든 — **스택이 포함된 ERROR 로그**가 남는다.
3. 같은 요청 ID가 브라우저 리포트·FE 로그·BFF에 모두 전달되므로, ID 하나로 전 구간을 추적할 수 있다.
4. 사용자에게는 정규화된 에러(재시도 가능 여부 포함)가 내려가 화면의 에러 UI가 처리한다.

### 시나리오 C — 운영자가 확인

- **Slack 알림**: Grafana 알림 룰(에러 로그 발생 시) → Slack 채널.
- **추이·집계**: Grafana 패널 (로그 기반 metric — 원본 로그를 스캔하지 않아 트래픽이 커져도 비용 일정).
- **앱 안에서**: admin 대시보드 페이지(예정)에서 최근 에러 목록·API 사용 top-N을 직접 확인.

## 5. 로그에 남는 것 (전부 3종)

모든 로그의 공통 키는 `requestId` — 브라우저가 만들어 FE와 BFF까지 흘러가는 추적 ID다.

| 이벤트 | 언제 | 담기는 것 |
|---|---|---|
| **접근 로그** (INFO) | 모든 API 요청마다 | 메서드, 경로, 상태코드, 소요시간, requestId, **어느 화면·무슨 행동에서 호출됐는지** |
| **서버 에러** (ERROR) | 라우트 예외, BFF 5xx | 스택 전체 + 요청 컨텍스트 |
| **브라우저 에러** (ERROR) | 렌더 에러, unhandled rejection | 메시지·스택, 페이지, 에러 종류, **직전 API 호출 10건** |

개인정보 보호: 요청/응답 **body와 쿼리스트링은 어떤 로그에도 남기지 않는다**
(공용 새니타이저가 강제하고 테스트로 잠가둠 — PII를 다루는 서비스이므로 절대 규칙).

## 6. 무엇이 이미 구현되어 있나

브랜치 `feat/observability-log-based` (이 PR). 신규 의존성 0.

| 묶음 | 내용 |
|---|---|
| 에러 바운더리 | `global-error` / 루트 `error` / `not-found` 신규 + 기존 바운더리에 재시도 연결 |
| 서버 로깅 | 구조화 로거(~30줄) + `handleUnexpectedError`·`withV1` 연결 → 60개 라우트 전부 커버 |
| 브라우저 캡처 | 전역 핸들러 + 스로틀 + 수신 라우트(검증·크기 제한·분당 캡) |
| API 컨텍스트 | 헤더 3종(`X-Request-Id`/`X-Client-Page`/`X-Client-Action`) + 링버퍼 + BFF 전달(allowlist) |

품질: 테스트 1,244개 통과(신규 67), codex(외부 모델) 리뷰 2회 — PII 로그 주입 가능성 등 8건 지적 → 전부 수정 후 결함 0.

## 8. 자주 나온 질문

- **BFF로 안 보내도 되나?** — 처음 "모두 BFF로 전송" 방침의 실제 의도는 "임의 목적지로 아웃바운드 불가"였다.
  stdout 수집은 플랫폼 몫이라 이 제약 밖이고, GCP 매니지드 서비스 활용은 확인 완료.
  한편 API 사용 이력은 어차피 **BFF가 모든 호출을 받으므로** 컨텍스트 헤더만 넘기면 BFF 쪽에도 남는다.
- **사용자가 많아지면?** — 집계는 metric(스캔 없음), 상세 조회는 24h 창 강제, 클라 리포트는 스로틀+서버 캡.
  장기 분석이 필요해지면 로그 sink → BigQuery(플랫폼 설정만). 미리 만들지 않는다.
- **소스맵 없이 브라우저 에러를 읽을 수 있나?** — 페이지+직전 호출 10건으로 대부분 특정 가능.
  빌드별 소스맵은 보관만 해두고 필요할 때 수동 디코드. 빈도가 높아지면 Bugsink 승격.
