# 논리 DB 스캔 성공 이력 조회 (7일) — 기능 요구서

> 작성일: 2026-08-07
> 대상: 백엔드(BFF) 구현 담당
> 상태: Draft — 구현 방식(2안) 선택 필요

## 1. 배경

논리 Database 목록을 기준으로 Airflow DAG가 GKE에 생성되어 스캔이 수행된다.
프론트에서는 "이 논리 DB가 최근 정상적으로 돌고 있는가"를 사용자에게 보여줘야 하는데,
현재 프론트가 쓸 수 있는 스캔 이력 API는 target source 단위(`/scan/history`)뿐이고
논리 DB 단위 실행 이력은 없다.

## 2. 요구사항

1. 논리 DB 단위로 **최근 7일간의 DAG 실행 이력**을 조회할 수 있어야 한다.
2. 이력은 **날짜별로 구분**되어야 한다. (프론트에서 7칸짜리 히스토리 스트립으로 렌더)
3. 각 논리 DB에 대해 **7일 중 1회라도 성공했는지 여부**를 판별한 결과를 함께 내려준다.
   - 이 판정 로직은 응답에 포함(예: `succeededWithinWindow`)해서 프론트가 재계산하지 않게 한다.
4. 조회 단위는 target source(또는 resource) 하나이며, 그 아래 논리 DB 전체를 한 번에 내려준다.
   - 논리 DB가 수십 개일 수 있으므로 논리 DB당 1회 호출은 피한다.

## 3. 성공 판정 정책 — 구현자 판단

아래는 판단이 필요한 지점만 나열한다. 정책 자체는 구현자가 정하고 문서에 남겨주면 된다.

- "성공"의 기준: DAG run state만 볼지, 마지막 task state까지 볼지, 부분 성공을 어떻게 볼지
- 7일 윈도우 기준: 실행 시각 기준 rolling 7일 vs 날짜(KST) 기준 7일
- 하루에 여러 번 실행된 경우 그 날의 대표 상태를 무엇으로 볼지
- 실행 자체가 없던 날의 표현 (성공/실패와 구분되는 별도 상태 필요 — 프론트에서 다르게 그림)
- 아직 실행 중(running/queued)인 건의 취급

## 4. 응답에 필요한 정보 (형태는 제안)

- 논리 DB 식별자: `databaseName`, `schemaName`, `type` (기존 `TestedLogicalDatabase`와 동일 키)
- 일자별 항목: 날짜, 상태, (가능하면) 마지막 실행 시각
- 윈도우 요약: 7일 내 1회 이상 성공 여부

기존 API 컨벤션을 따른다: snake_case wire, `/install/v1/target-sources/{targetSourceId}/...` 하위.
확정되면 swagger에 반영 후 프론트가 그 스키마만 보고 붙인다.

## 5. 구현 옵션

둘 중 하나를 선택해 주세요. GCP Composer는 모두 OpenLineage를 지원하는 버전입니다.

**A안. OpenLineage 이벤트 활용**
- Composer가 내보내는 lineage 이벤트를 수집·저장해 두고 조회
- 논리 DB(=데이터셋) 단위 매핑이 자연스럽고, 이력 보관 기간을 우리가 통제 가능
- 이벤트 수집/저장소가 추가로 필요

**B안. Composer Airflow REST API 직접 조회**
- Composer의 Airflow REST API(`dagRuns` 등)를 BFF에서 호출
- 추가 인프라 없이 시작 가능
- DAG ↔ 논리 DB 매핑을 DAG 이름 규칙 등으로 풀어야 하고, 호출량/레이트리밋과 Composer 가용성에 응답이 묶임

선택 시 함께 알려주실 것: 응답 지연 수준(동기 조회 가능 여부), 캐시/보관 전략, DAG ↔ 논리 DB 매핑 방식.
