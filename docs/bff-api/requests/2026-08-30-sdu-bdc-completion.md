# SDU BDC 구축 완료 — 관리자가 단언한다 (08-28 핸드오프 델타)

- 대상: `install/v1` BFF, base `/install/v1/target-sources/{targetSourceId}/sdu`
- 요청자: Pass FE
- 작성일: 2026-08-30
- **이 문서는 델타다.** `2026-08-28-sdu-be-handoff.md` 를 읽은 뒤에 읽는다. 아래에 적히지
  않은 것은 그 문서 그대로이고, 절 번호(§n)는 전부 그 문서의 것이다.

## 0. 무엇이 바뀌나

08-28 §8 은 `bdc.status` 를 **서버가 파생하는 값**으로 적었다 — 두 확인과 수신자 수를 보고
서버가 계산하고, 완료 전에 조건 하나를 잃으면 `NOT_STARTED` 로 되돌아간다.

오너 결정(2026-08-30)으로 **완료는 파생이 아니라 단언이 된다.** 관리자 운영 콘솔에 버튼이
하나 서고, 그 버튼이 「BDC 쪽 리소스 구축이 끝났다」고 말한다. 신규 오퍼레이션 **1건**과
`bdc` 응답의 필드 **하나**(§3.1)가 전부이고, 08-28 의 나머지는 그대로다.

바뀌는 것이 플래그 하나가 아닌 이유는 §8 이 이미 적어 두었다 — `COMPLETED` 는 대상 소스를
ProcessStatus **5**(`WAITING_CONNECTION_TEST`)로 옮긴다. **그래서 이 버튼은 설치를 한 칸
밀어낸다.** 08-28 이 이 값을 두 곳에서 다르게 말하고 있었고, 이 문서가 그것을 정리한다
(§3.2).

파생이 통째로 사라지는 것은 아니다. `NOT_STARTED ↔ IN_PROGRESS` 는 그대로 §8 의 계산이고,
단언이 덮는 것은 **완료 하나**다.

## 1. 신규 엔드포인트 — 1건 (§2 에 여덟 번째 행이 붙는다)

| Method | Path | 설명 |
| --- | --- | --- |
| PUT | `/install/v1/target-sources/{targetSourceId}/sdu/upload/bdc/completion` | BDC 구축 완료 **단언**(되돌리기 포함) |

```jsonc
// body
{ "completed": true }        // false 는 되돌리기 (§3)

→ 204                        // 본문 없음
→ 400  INVALID_PARAMETER     // completed 가 boolean 이 아님 · 단언의 전제 미충족 (§4)
→ 403  FORBIDDEN             // 담당자 권한으로 호출 (§2)
→ 404                        // SDU 대상 소스가 아님
```

에러 응답은 §1 의 `ErrorMessage` 그대로다.

```jsonc
{
  "timestamp": "2026-08-30T02:27:09.123Z",
  "status": "BAD_REQUEST",
  "code": "INVALID_PARAMETER",
  "message": "BDC 진행 조건을 갖추지 못했습니다.",
  "path": "/install/v1/target-sources/1100/sdu/upload/bdc/completion"
}
```

**경로는 §5 응답의 블록 이름을 따라간다.** `GET /upload` 가 `bdc` 라고 부르는 것을 쓰기도
`…/upload/bdc/…` 로 부른다 — §6 이 `access_key_recipients` 에 대해 세운 규칙 그대로,
**쓰기가 읽기를 그대로 비춘다.**

**되돌리기에 두 번째 경로를 만들지 않는다.** §7 이 확인을 두 경로로 가른 것은 방화벽과
업로드가 **서로 다른 사실**이기 때문이었다. 여기서 사실은 하나이고 값이 둘이라, §12.3 이
`YES/NO` 를 접은 자리와 같다 — 이름 둘인 값 둘은 boolean 하나다. 경로가 가를 것이 없으므로
본문에 남는 것도 `completed` 하나다.

**응답 본문은 없다.** 화면은 `GET /upload` 와 `GET /process-status` 를 다시 읽어 결과를
안다 — §4 제출과 §7 확인이 이미 그 모양이고, 이쪽 클라이언트는 204 에서 본문을 읽지 않는다.

## 2. 권한 — 이 한 건만 ADMIN 전용이다

§10 은 신규 일곱 건이 **전부 담당자**(ADMIN 통과)라고 적었고, 「ADMIN 전용 신규
엔드포인트는 없다」고 못박았다. **여덟 번째가 그 문장을 깬다.**

| # | 엔드포인트 | 권한 |
| --- | --- | --- |
| 8 | `PUT /sdu/upload/bdc/completion` | **ADMIN 전용** — 담당자는 403 |

§10 의 기준은 그대로 쓴다 — **화면이 누구 것인가.** 앞의 일곱은 담당자 상세 페이지가
부르고, 이 한 건은 **관리자 운영 콘솔의 진행 상태 탭**이 부른다. 담당자 화면에는 이 버튼이
없다.

기준이 같아도 굳이 한 절을 쓰는 이유는, 이 쓰기가 앞의 일곱과 **다른 종류의 말**을 하기
때문이다. 확인 답변은 담당자가 **자기 쪽 사실**을 보고하는 것이고(방화벽이 열렸다, 파일이
올라갔다), 이것은 **BDC 쪽 작업**에 대한 단언이다. 담당자에게 이 버튼을 주면 담당자가 제
설치를 스스로 다음 단계로 밀어낼 수 있게 되는데, SDU 에는 승인 단계가 없어서(§0) 그 앞을
막아 줄 것이 아무것도 없다.

## 3. §8 이 이제 뜻하는 것

§8 의 네 줄 중 **둘째 줄만** 바뀐다.

| §8 의 규칙 | 08-28 | 지금 |
| --- | --- | --- |
| 두 확인 + 수신자 1명 이상 → `IN_PROGRESS` | 서버 파생 | **그대로** |
| 완료되면 `COMPLETED`, ProcessStatus 5 | 서버 파생 | **관리자 단언**(§1). 5 는 그대로 맞다 (§3.2). 이 조건을 **전제로 요구한다** (§4) |
| 완료 전 조건을 잃으면 `NOT_STARTED` 로 되돌아감 | 서버 파생 | **그대로** — 완료 전에만 (§6 #1 이 그 뒤를 묻는다) |
| `reset` 이 BDC 를 버린다 | 파생이라 자동 | **이름을 불러 지운다**, 무조건 (§5) |
| 화면은 BDC 를 상세히 그리지 않는다 | | **그대로** |

### `completed: true`

1. `bdc.status` 를 `COMPLETED` 로, `bdc.completed_at` 을 지금으로, `bdc.completed_by` 를
   호출한 관리자로 세운다 (§3.1)
2. 대상 소스가 ProcessStatus 5 **아래**에 있으면 5(`WAITING_CONNECTION_TEST`)로 옮긴다.
   이미 5 이상이면 옮기지 않는다 — 6·7단계 대상을 5 로 끌어내리는 것은 전진이 아니다 (§3.2)
3. 단, **전제를 갖추지 못했으면 아무것도 하지 않고 400 이다** (§4)

### `completed: false` — 되돌리기

1. `bdc.completed_at` 과 `bdc.completed_by` 를 `null` 로 지우고, `bdc.status` 를 **§8 의
   파생이 지금 무엇이라고 하는지로** 되돌린다. 조건을 갖추고 있으면 `IN_PROGRESS`, 아니면
   `NOT_STARTED` 다. 단언을 지우면 남는 것은 계산이고, 그 계산은 §8 이 이미 적어 두었다
2. **ProcessStatus 는 움직이지 않는다.** 5 로 간 대상은 5 에 남는다 — 그 사이에 연결
   테스트가 이미 돌았을 수 있고, 4단계로 되돌리면 그 실행 기록이 도달할 수 없는 단계의
   산물이 된다. 되돌리기가 취소하는 것은 **단언**이지 그 뒤에 일어난 일이 아니다
   (§6 #3 이 이것을 다시 묻는다)
3. `COMPLETED` 가 아니었어도 **거절하지 않는다.** 결과가 이미 그 값이라 400 은 관리자가
   할 수 있는 일이 없는 거절이다 — 멱등하게 204 다

### 3.1 `bdc.completed_by` — §5 응답에 한 칸 는다

```jsonc
"bdc": {
  "status": "COMPLETED",
  "checked_at": "2026-08-30T07:50:00Z",
  "completed_at": "2026-08-30T07:41:00Z",
  "completed_by": { "id": "admin-1", "name": "관리자", "email": "admin@company.com" }
}
```

08-28 §5 의 `bdc` 에는 사람이 없었다. **그때는 저자가 없었기 때문이다** — 파생값은 아무도
만들지 않는다. 단언에는 저자가 있고, 그 단언 하나가 대상 소스를 ProcessStatus 5 로 옮긴다.
담당자의 두 확인이 `acked_by` 를 지는 것과 같은 이유이고, 모양도 같다
(`{ id, name, email }`).

되돌리기와 초기화가 `completed_at` 과 **함께** 비운다 — 지워진 단언에 저자만 남으면 그
이름은 일어나지 않은 일에 붙어 있게 된다.

**화면은 이 값을 「담당자 확인」 카드의 BDC 줄에 그대로 쓴다** — 같은 카드의 두 확인이 이미
「예 · 홍길동 · 08-25 10:40」을 쓰고 있어서, 셋째 줄만 시각으로 끝나면 한 카드 안에서 문법이
갈리고 BDC 만 저자 없는 사실로 읽힌다. 값이 비어 있으면(옛 단언, 혹은 상류가 안 보내는 경우)
시각만 서고 구분자도 서지 않는다 — 미답에 사람을 붙이지 않는 `acked_by` 와 같은 처리다.

### 3.2 목적지는 **5**다 — 08-28 의 모순을 여기서 닫는다

08-28 은 같은 사실을 두 곳에서 다르게 말한다.

| 어디 | 무엇이라고 하나 |
| --- | --- |
| §8, 「완료되면 `COMPLETED` 이고, 대상 소스는 ProcessStatus **5**(`WAITING_CONNECTION_TEST`)로 간다」 | 5 로 간다 |
| §9 진행 상태 행, 「7단계 레일에서 **2·3·5 비활성**」 | 5 는 SDU 가 밟지 않는 칸 |

**둘 다 참일 수 없고, §8 이 맞다. §9 의 「2·3·5」에서 `5` 가 오기다** (오너 2026-08-30
「그냥 이건 step1->4->5->7 이렇게 할게. 안 바꿀게」). SDU 가 건너뛰는 것은 **2 와 3 뿐**이다.

의미로도 §8 쪽이 맞다. 대상은 단언 직후 실제로 「연결 테스트 필요」에 **앉는다** — 그리고
그래야 **승인 조건 ②(최신 연결 테스트 성공)를 무언가가 만족시킬 수 있다.** 5 를 건너뛰면
「이제 연결 테스트의 차례다」라고 말하는 상태가 흐름에서 사라지고, 조건 ② 는 아무도 촉발하지
않는 행위를 기다리게 된다.

**그리고 코드가 이미 그렇게 말하고 있다.** `lib/process/calculator.ts` 는 ProcessStatus 를
프로젝트 상태에서 파생하는데, 거기서 **6 은 「연결 테스트가 한 번이라도 성공했다」는 뜻이다**
(`status.connectionTest.passedAt` 이 있어야 6, 없으면 5). BDC 구축 완료 단언은 연결 테스트를
통과한 적이 없으므로, 6 을 쓰는 것은 **시스템의 나머지가 거짓이라고 정의한 것을 사실로 적는
일**이 된다 — 실제로 6 을 써 보면 그 값을 다시 계산하는 어느 경로든 5 로 되돌린다. 목적지가
5 여야 한다는 것은 취향이 아니라 이 저장소가 이미 세워 둔 정의다.

**이 엔드포인트의 전이는 「5 아래면 5 로」 하나뿐이다.** 5 → 6 → 7 구간은 관리자 승인 CTA 의
것이고 여기서 건드리지 않는다 — 6 은 연결 테스트가 실제로 통과했을 때 그 경로로 온다.

**다음 읽는 사람에게**: §9 의 「2·3·5 비활성」을 보고 이 문서를 의심하지 말 것. 비활성인 것은
2·3 이고, 그 줄의 `5` 는 여기서 §8 쪽으로 정리됐다.

### FE 는 ProcessStatus 를 움직이지 않는다

이 두 동작 중 어느 쪽에서도 **화면은 단계를 옮기지 않는다.** 쓰기가 204 로 돌아오면 화면은
`GET /upload` 와 `GET /process-status` 를 **다시 읽고**, 거기 적힌 것을 그린다. 서버가 5 로
옮기지 않기로 하면 화면은 옮기지 않은 것을 그린다 — 낙관적 갱신도, FE 쪽 단계 계산도 없다.

## 4. 전제 — 단언에만 있다

**`completed: true` 는 §8 의 `IN_PROGRESS` 진입 조건을 그대로 요구한다** (오너 2026-08-30,
담당자 확인 줄을 가리키며 「이거 다 미답이면 「구축 완료」를 못 하게 해」). 즉 현재 정의의
모든 Region 이 두 목록 모두에서 확인 「예」이고, S3 Access Key 수신자가 1명 이상이어야 한다.
못 갖췄으면 400 `INVALID_PARAMETER` 이고 아무것도 바뀌지 않는다 — `bdc.status` 도, 단계도.

이유는 앞뒤가 맞지 않기 때문이다. **시작조차 할 수 없었던 일이 끝났을 수는 없다.** BDC 는
아무도 결재하지 않은 방화벽과 아무도 `ls` 해 보지 않은 경로 위에 리소스를 만든 적이 없으므로,
그 대상에 대해 「구축이 끝났다」는 단언은 참일 여지 자체가 없다.

> **읽은 방식을 밝혀 둔다.** 「다 미답이면」을 **전제 전체**(두 확인 「예」 + 수신자 1명 이상)로
> 읽었지 「모든 항목이 미답일 때만 막는다」로 읽지 않았다. 확인 하나만 들어온 대상도 BDC 는
> 시작하지 못했으므로 같은 이유로 막힌다. 느슨한 쪽을 의도하셨다면 이 문단 하나가 바뀐다.

**되돌리기(`false`)에는 전제가 없다.** 오너의 「언제든」은 그 방향에 그대로 남는다 — 되돌리기는
사실을 주장하는 것이 아니라 주장을 거두는 것이고, 거둘 수 없는 상태라는 것은 없다.

### 모달은 여전히 실제 상태를 보여준다

전제가 돌아왔다고 해서 확인 모달이 하던 일이 없어지지 않는다. 모달은 「세 가지를 모두
확인하셨나요?」 아래 세 항목 옆에 **콘솔이 아는 실제 상태**를 적는다 — 스캔 판정과 확정 여부,
두 Terraform 작업의 적용 상태. 둘은 서로 다른 것을 막는다:

- **서버의 400** 은 §8 이 「참일 수 없다」고 말하는 것을 막는다. 관리자가 넘길 수 없다
- **모달** 은 §8 이 모르는 것을 **보여준다.** 스캔이 실패했거나 Terraform 이 미적용인
  대상에서도 전제는 성립할 수 있고, 그때 단언은 계약상 유효하지만 사실과 어긋날 수 있다.
  그 판단은 관리자의 것이고, 모달은 무엇을 덮어쓰는지 읽게 한 뒤 넘긴다

BDC 쪽 사실을 이 콘솔이 전부 읽을 수 있는 것도 아니다 — Glue 설정은 못 읽고, 모달은 못 읽는다고
적는다. 서버가 아는 조건만으로 내리는 거절이 **유일한** 방어선이 될 수 없는 이유가 그것이다.

### 화면

CTA 는 전제를 못 갖추면 **잠기고, 왜 잠겼는지 말한다** — 「방화벽 결재 확인과 데이터 업로드
확인이 모두 「예」이고 S3 Access Key 수신자가 1명 이상이면 처리할 수 있어요.」 이유 없는 비활성
버튼은 무엇을 기다려야 하는지 말하지 않는다. 서버가 세는 셋을 화면도 같은 셋으로 센다.

## 5. 초기화 — 단언도 무조건 버린다

§8 은 `POST …/reset` 이 SDU 에서 업로드 상태(확인 답변 · 수신자 · BDC)만 버리고 연동 대상
정의는 남긴다고 적었다. 그때 BDC 는 파생값이라 「버린다」가 곧 「다시 계산한다」였다.

이제는 **이름을 불러 지워야 한다**: `bdc.status` · `bdc.completed_at` ·
`bdc.completed_by` 셋 다, **무조건**. 누가 언제 단언했든, 대상 소스가 몇 단계에 있든
봐주지 않는다. 초기화는 그 연동을 없던 일로 하는 것이고, 단언된 완료는 초기화가 비켜갈
이유가 되지 못한다 — 비켜가면 1단계로 돌아간 대상이 「BDC 구축 완료」를 달고 서 있게 된다.

## 6. 확인이 필요한 것

§11 과 같은 표다. 각 항목이 답에 따라 화면을 바꾼다.

| # | 질문 | 다르게 답하면 |
| --- | --- | --- |
| 1 | 관리자가 `COMPLETED` 를 단언한 **뒤에** 담당자가 확인을 무효화하면(§3.1) 완료가 살아남나, §8 의 「조건을 잃으면 되돌아간다」가 여전히 적용되나 | 살아남으면 카드는 계속 「구축 완료」와 되돌리기 버튼을 그린다. 적용되면 관리자가 누른 적 없는데 완료가 사라지고, 화면에는 그 이유를 적을 자리가 없다 — 무효화 안내(§3.1)는 담당자의 두 확인을 설명하지 BDC 를 설명하지 않는다. 전제(§4)는 **단언하는 순간**만 지킨다 — 그 뒤로 조건이 참으로 남게 하는 것은 아무것도 없고, 이 질문은 바로 그 뒤를 묻는다 |
| 2 | **§11 #8 이 날카로워졌다.** BDC 완료 **후에** 대상을 추가하면 BDC 가 다시 도나 | 파생이던 시절에는 조건이 깨지며 서버가 알아챌 여지가 있었다. **단언된 완료는 새 대상을 알아챌 수 없다** — 관리자가 다시 누르지 않는 한 추가된 대상은 영원히 반영되지 않고, 화면은 「구축 완료」라고 적은 채로 서 있는다 |
| 3 | 되돌리기가 ProcessStatus 도 4 로 되돌려야 하나 (제안: 아니오, §3) | 되돌린다면 5단계에서 이미 돌아간 연결 테스트 실행이 4단계 대상에 매달리고, 연결 테스트 탭은 실행 기록이 있는데 실행 버튼이 잠긴 화면이 된다 |
| 4 | 5·6·7단계에 도착한 대상에서 되돌린 `bdc` 는 **무슨 뜻인가.** 누를 수 있다는 것은 정해졌지만(오너 「구축 완료 롤백은 언제든」, §4), 「연동 완료된 대상의 BDC 가 미완료」라는 상태를 어떻게 읽어야 하는지는 정해지지 않았다 | 정상 값이라면 화면은 그 조합을 아무 말 없이 그려야 하고, 있어서는 안 될 값이라면 어딘가가 그것을 말해야 한다 — 지금은 둘 다 아니라서 카드가 조용히 모순을 그린다 |

**이미 답이 나온 것**

- **단언에는 전제가 있고 되돌리기에는 없다** (오너 2026-08-30). §4. 그리고 이 규칙이
  앞선 질문 하나를 함께 닫는다 — 「제출조차 안 한 1단계 대상도 단계를 뛰나」는 **뛰지
  않는다**: 1단계 대상은 두 확인도 수신자도 없어 전제를 못 갖추므로 400 이고, 단계가
  움직이지 않는다. 「5 아래면 5 로」는 전제를 통과한 뒤에야 적용된다
- **목적지는 5다** (오너 2026-08-30, 「step1->4->5->7」). 08-28 §8 의 「ProcessStatus 5」가
  맞고 §9 의 「2·3·5 비활성」에서 `5` 가 오기다 (§3.2)
- **`completed_by` 를 싣는다** (오너 2026-08-30). 파생값에는 저자가 없었지만 단언에는
  있다 (§3.1)
- **초기화는 단언도 무조건 버린다** (오너 2026-08-30). §5
- 완료를 **버튼 하나**로 할지 항목별 체크로 할지 — 모달이 세 항목을 묻되 서버로 가는 값은
  `completed` 하나다(오너 2026-08-30). 세 항목은 관리자의 확인 절차이지 서버가 저장할
  사실이 아니라, 계약에 자리를 만들지 않는다
- 되돌리기가 `bdc` 만 되돌리고 ProcessStatus 는 서버가 정한다는 것(오너 2026-08-30).
  §3 이 그 결정의 기록이고, #3 은 서버가 정할 값 자체를 묻는다
- **400 의 `message` 를 화면이 쓸 수 있는지는 더 이상 질문이 아니다.** 전제 미충족 400 이
  사라지면서(§4) 남은 400 은 본문이 boolean 이 아닌 경우 하나뿐인데, 그건 관리자가 마주칠
  상태가 아니라 클라이언트의 버그다 — 화면에 옮겨 적을 문장이 애초에 없다
