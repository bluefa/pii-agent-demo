# Admin Pipeline — 4페이지 정보 계층 정리

> **반영 현황**: §1 대시보드 = 오너 승인 후 HTML 반영 완료 (2026-07-04) —
> 카드 6→3장(TF task 카드는 서브텍스트 아닌 완전 제거 채택), FAILED 우선 정렬 채택,
> 목록 유형·생성일 열 보강 채택. §2~§4는 오너 피드백 대기.

> 목적: 각 페이지가 **실제로 렌더하는 정보 전수**를 나열하고, 정보마다
> ①어느 계층에서 ②어떤 방식으로 보여줄지, ③lazy loading·제외 대상을 판정한다.
> 오너 피드백 전까지는 초안 — 화면·코드 변경 없음.
>
> 인벤토리 출처: `admin-pipeline.html` 렌더 함수 전수 판독
> (viewDashboard/renderPeriod/renderList, viewServices/renderSvcList/renderTsPanel,
> viewTarget, viewPipeline/renderTaskDetail, openPreview/openCancel).

## 0. 판정 기준과 계층 어휘

정보의 계층은 장식이 아니라 **"운영자가 이 페이지에서 답하려는 질문"의 빈도×긴급도**로 정한다.
질문에 답하지 않는 정보는 아무리 API에 있어도 화면에 올리지 않는다.

| 계층 | 의미 | 표현 방식 | 로딩 |
|---|---|---|---|
| **T1** | 페이지의 존재 이유. 열자마자 0.5초 안에 읽혀야 함 | 최상단, 가장 큰 시각 요소 | 초기 로드 |
| **T2** | 스캔 대상 본문 (목록·그리드·흐름) | 본문 영역, 행 단위 | 초기 로드 |
| **T3** | 맥락·보조. 있어야 하지만 시선을 끌면 안 됨 | 작은 meta 텍스트, 요약 칩 | 초기 로드 |
| **T4** | 필요할 때만. 평소엔 숨김 | 클릭·접힘(collapsible)·hover 뒤 | **lazy** (해당 시점에 API 호출) |
| **X** | 이 페이지에서 제외 | 삭제 (다른 페이지 몫이거나 아예 불필요) | 호출 안 함 |

원칙 3개:

1. **식별자는 계층의 왕이 아니다** — id·계정 같은 식별 정보는 breadcrumb/meta 행(T3)이면 충분.
   T1은 항상 "상태·문제·다음 행동".
2. **API에 있다 ≠ 화면에 필요하다** — 응답 필드를 그대로 나열한 것이 현재 과밀의 주원인.
3. **미제공/null 필드는 화면에 자리를 갖지 않는다** — 값이 생기면 그때 합류.
   부재 설명은 설계 문서 몫.

## 1. 대시보드 (#/dashboard)

**이 페이지의 질문**: ① "지금 실패한 거 있나?" (긴급) ② "지금 뭐가 돌고 있나?" (빈번)
③ "특정 파이프라인 찾아 들어가기" (빈번)

### 인벤토리와 판정

| # | 현재 표시 정보 | 현재 위치 | 판정 | 근거 |
|---|---|---|---|---|
| 1 | 동작 중 파이프라인 수 (RUNNING count) | 실시간 stat 카드 1 | **T1** | 질문 ② 직답 |
| 2 | 사용/총 slot 리밋 — 분모 미제공(`—`) | 실시간 stat 카드 2 | **X 제외** | 미제공 값을 위한 상설 카드. 분모가 제공되는 날 #1 카드의 분모로 합류하면 됨 |
| 3 | 동작 중 Terraform task 수 (근사 배지) | 실시간 stat 카드 3 | **X 제외** (또는 #1의 서브텍스트) | worker 부하 근사치 — 운영자 질문 어디에도 직답 아님. "근사" 배지를 달아야만 성립하는 숫자는 T1 자격 미달 |
| 4 | 기간 통계 — 실패 수 (1h/1d/7d) | 기간 stat 카드 | **T1** | 질문 ① 직답. >0이면 페이지에서 가장 강조 |
| 5 | 기간 통계 — 성공 수 | 기간 stat 카드 | **T2** | 정상성 확인용 보조 |
| 6 | 기간 통계 — 실행 중 수 | 기간 stat 카드 | **X 제외** | #1(실시간 RUNNING)과 의미 중복·혼동 ("기간 내 생성됐고 아직 실행 중"을 구분해 읽을 운영자 없음) |
| 7 | 기간 선택 seg (1시간/1일/7일) | 섹션 타이틀 우측 | T3 (유지) | #4·#5의 컨트롤 |
| 8 | 목록 필터 (target 검색·상태·provider) | 목록 카드 상단 | T3 (유지) | 질문 ③의 도구 |
| 9 | 목록 행: target id | 테이블 | **T2** | 행 식별 |
| 10 | 목록 행: provider (+외부 배지) | 테이블 | **T3** | 보조 식별 — 지금처럼 중립 텍스트+dot 유지 |
| 11 | 목록 행: 상태 pill | 테이블 | **T2** | 스캔의 축 |
| 12 | 목록 행: 진행 N/M 바 | 테이블 | **T2** | 상태의 정도 |
| 13 | 새로고침 버튼 / 페이지네이션 | 목록 카드 | T3 (유지) | 도구 |

### 빠져 있는 정보 (보강 — 빼기만이 정리가 아님)

| 정보 | 계층 | 근거 |
|---|---|---|
| 목록 행: **유형 (INSTALL/DELETE)** | T2 | 같은 target에 설치·삭제가 섞이면 상태만으로 행 구분 불가 (target 페이지 이력 테이블엔 이미 있음 — 대시보드만 누락) |
| 목록 행: **생성/마지막 활동 시각** | T3 | "언제부터 돌고 있지?"는 triage 기본 질문인데 대시보드 목록에 시간 축이 전무 |
| **FAILED 우선 정렬 or 상단 고정** | T1 규칙 | 실패가 5페이지 뒤에 있으면 질문 ①에 답 못 함. id desc 정렬 대신 `FAILED > RUNNING > 나머지, 각 그룹 내 최신순` 제안 |

### 로딩

- 초기: live count 1개 + 기간 실패/성공 + 목록 1페이지 (API 2~3회).
- seg 변경·페이지 이동 시에만 해당 구간 재호출. lazy 대상 없음 (제외로 해결).

**요약**: 상단 stat 카드 6장 → **3장** (RUNNING now / 기간 실패 / 기간 성공). 실패 강조가 유일한 색.

## 2. 서비스·대상 검색 (#/services)

**이 페이지의 질문**: 단 하나 — "작업할 target을 찾아 들어간다." 허브(경유지)이지 대시보드가 아님.

### 인벤토리와 판정

| # | 현재 표시 정보 | 현재 위치 | 판정 | 근거 |
|---|---|---|---|---|
| 1 | 서비스 검색 input | 좌측 카드 | T2 (유지) | 진입 도구 |
| 2 | 서비스 목록 (name + code) | 좌측 카드 | **T2** | 선택 대상 |
| 3 | 선택 서비스의 target source 목록 (provider, tsId) | 우측 카드 | **T2** | 선택 대상 |
| 4 | **(참고) 서비스 권한 사용자 목록** | 하단 collapsible | **X 제외** | 아래 별도 설명 |

#### "권한이 있는 유저"가 왜 있었나 → 제외 근거

원본 API(`getUserServices`) 응답에 권한 사용자가 포함되어 있어서 **"API에 있으니 실었다"** —
위 원칙 2 위반의 전형. 이 페이지의 질문("target 찾기")에 아무 답도 하지 않고,
파이프라인 운영 플로우 어디에서도 소비되지 않는다.

- 판정: **제외**. API 호출 자체를 하지 않는다.
- 만약 미래에 "이 서비스 담당자가 누구지?"(장애 문의 라우팅) 요구가 생기면:
  그건 서비스 상세 정보라 **target 페이지 또는 별도 서비스 상세의 T4(접힘+lazy)** 자리.
  검색 허브의 상설 요소로 돌아올 일은 없음.

### 빠져 있는 정보 (보강)

| 정보 | 계층 | 근거 |
|---|---|---|
| target 행에 **설치 상태(processStatus)** 칩 | T2 | "어느 target에 들어갈까"의 판단 재료 — 지금은 provider와 id뿐이라 클릭해 봐야 앎 |
| target 행에 **진행 중 파이프라인 여부** (RUNNING 표시) | T3 | 같은 이유. 점 하나/작은 pill 수준이면 충분 |

### 로딩

- 초기: 서비스 목록만.
- **target source 목록 = lazy** (서비스 선택 시 `getTargetSourcesByServiceCode`) — 현 구조 그대로.
- 권한 사용자 API: 호출 제거.

**요약**: 화면 요소 4개 중 1개 제외, target 행의 판단 재료만 보강. 이 페이지는 가벼울수록 좋다.

### 빠져 있는 정보 (보강)

| 정보 | 계층 | 근거 |
|---|---|---|
| **CSP별 metadata** (awsAccountId·linkedAccount·regionType·TF권한 / tenantId·subscriptionId / gcpProjectId) | **T3 — IdentityBar 카드 내 상시 노출** (2026-07-05 오너: "접었다 폈다 불필요, 카드 하나에") | detail-ia.md "본진은 target 페이지" 이행. 접힘(T4)안 폐기 — 행 수가 최대 4개라 접을 만큼 무겁지 않음. 필드 없는 IDC는 구간 생략 |

### 로딩

- 초기: 헤더(공통 필드) + 최근 파이프라인 + 이력 1페이지.
- **CSP metadata = lazy 허용** — 헤더 API 응답에 이미 포함되면 그냥 접힘에 넣고,
  별도 API라면 접힘을 열 때 호출.

**요약** (2026-07-05 최종): 그룹 3개 — ① **대상**(IdentityBar 카드 하나: CSP+TargetSourceId
+CSP metadata 상시, 계정·설치 상태 표시 제거) ② **파이프라인 상태**(상태 바 + 액션 버튼
= 한 그룹 — 행동 가능 여부는 상태에서 파생) ③ **이력**(과거). 시간축 정렬:
무시간(식별) → 현재(상태·행동) → 과거(이력).

## 4. 파이프라인 상세 (#/pipeline/:id)

**이 페이지의 질문** (detail-ia.md §2에서 확정): ① "지금 어떤 상태야?" ② "문제 있어? 어디서?"
③ "뭘 대상으로 한 작업이지?" ④ "언제 시작했고 얼마나 걸리고 있지?" ⑤ (드묾) "멈춰야 하나?"

v2 재배치가 이미 반영된 페이지라 대체로 정합 — 잔여 과밀만 판정한다.

### 인벤토리와 판정

| # | 현재 표시 정보 | 현재 위치 | 판정 | 근거 |
|---|---|---|---|---|
| 1 | 상태 pill(대형) + 진행 바 + 현재 task + [취소] | 상태 바 1행 | **T1** (유지) | 질문 ①⑤ — v2 목적 그대로 |
| 2 | error_code 요약 (FAILED일 때만) | 상태 바 1행 | **T1** (유지) | 질문 ② — 조건부 노출 규칙이 모범 |
| 3 | 상태 바 meta: type·#id·**레시피**·provider·target·서비스·생성·마지막활동·단계 | 상태 바 2행 | **T3** (2026-07-05 개정) | 다이어트(→5개) 판정을 오너 지시("메타데이터가 풍부한데 안 쓴다")로 갱신 — recipe_definition·단계를 편성. 운영 신호(next_due·재시도 예산·취소 요청)는 meta가 아니라 **1행(T1)**에 조건부 노출 |
| 4 | Task 흐름 (노드: seq·kind칩·operation·상태·fail·시각) | 본문 좌 | **T2** (유지) | 질문 ①② 본문 |
| 5 | Task 상세 사이드 패널 — 공통 kv (operation·타이밍 설정·fail/maxFail·started/finished) | 본문 우 | **T4** (유지) | 노드 클릭 뒤에만 — 현 구조 적절 |
| 6 | 〃 attempts 테이블 (#·상태·error_code·시각·raw response) | 사이드 패널 | **T4** (유지) | 〃. raw response ellipsis+title 유지 |
| 7 | 〃 check kv 중 `last_response_code`/`last_response_summary` — 항상 null + "미채움" 배지 | 사이드 패널 | **X 제외** | 원칙 3 — null 필드의 상설 나열. 값이 채워지는 날 행 추가 |
| 8 | 〃 "설정은 읽기 전용 — PATCH 없음" 안내문 | 사이드 패널 | **X 제외** | 구현 계약 설명 — 운영자 질문 아님. components.md에 이미 있음 |
| 9 | 〃 "job_ids·dispatch_response_* 는 제거된 필드…" 안내문 | attempts 하단 | **X 제외** | 〃 (없어진 필드 이야기를 화면이 할 이유 없음) |
| 10 | 대상 상세 metadata 접힘 (CSP kv + target 링크) | 하단 collapsible | **T4** (유지) | 질문 ③ — 접힘 수위 적절 |
| 11 | ~~"실행 메타 (ADR-021) — 미제공"~~ → **실행 스케줄 메타(실필드)** | 하단 collapsible | **T4 재편성** (2026-07-05) | 최신 main이 next_due_at·leased·cancel_requested·due_lag를 **실제 제공** — "필드가 제공되는 날 재편성" 조건 성립. next_due_at·cancel_requested는 T1(상태 바)에도 조건부 승격 |
| 12 | status=**PENDING**(시작 지연, LIN-30) + next_due_at 시작 예정 | 상태 바 1행 | **T1 신규** (2026-07-05) | "지금 어떤 상태야?"의 새 답 — 대기 중이면 "언제 시작하나"가 즉답이어야 함 |

### 로딩

- 초기: 파이프라인 단건 + tasks 요약 (A4 한 번).
- **attempts / check 상세 = lazy 후보** — 노드 클릭 시 호출(task당 1회 캐시).
  D1 API가 tasks에 내장해 주면 굳이 쪼개지 않아도 됨 (계약 확정 시 재판정).
- CSP metadata 접힘 = target 페이지와 동일 규칙.

**요약**: 구조는 유지, **설명문 3개 + null 필드 2행 + ADR-021 섹션 제거**, meta 행 7→5개.
이 페이지의 잔여 과밀은 전부 "시스템이 자기 구현 사정을 화면에서 해명하는 텍스트"였다.
