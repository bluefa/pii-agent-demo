고치는 것. D1 — 39% 공백이 계약 사실 9줄로 바뀐다. 그리고 실행하면 온 코드의 행을 짚어 줄 수 있다. 남는 것. D2 — 표면 대비는 그대로다. 즉 C 는 A·B 와 경쟁하지 않는다: C 는 빈 칸을, A·B 는 표면을 고친다.

판정 — A + C

  • C 는 무조건 넣는다. 세 시안 중 D1(모달의 39%가 상시 공백)을 고치는 것은 C 뿐이고, 채우는 재료가 발명이 아니라 계약이다. Swagger UI 가 실행 전 칸을 비우지 않는 이유가 정확히 이것이다.
  • 표면은 A. B 는 신택스 색을 넣으면서 좌우를 더 닮게 만든다 — 두 JSON 을 대조하는 화면에서 요청과 응답이 같은 색이면 대조의 기준이 사라진다. A 는 이 레포에 이미 선례가 있어 새 색을 발명하지 않는다(--pl-gray-800 + --pl-chrome-item + logAnsi).
  • A 의 약점은 C 가 정확히 지운다. "빈 검은 칸이 더 크게 비어 보인다"가 A 의 유일한 실점이고, C 를 얹으면 그 칸은 실행 전에도 비지 않는다. 두 시안이 서로의 결함을 덮는다.
  • 공통으로 가져오는 것 — gutter 라인 넘버(D3), Parameters 표 머리(D5), [METHOD][URL][저장] 한 줄(D6), status 알약 + Created · 24 ms · 412 B(D7).
  • 안 가져오는 것 — 코드 폴딩·드래그 divider·응답 탭(Headers/Cookies). 계약이 opaque object 하나라 탭이 나눌 것이 없고, 폴딩은 이 크기의 JSON 에 값하지 않는다.
