## 핵심 원칙

**피드백은 액션이 일어난 자리에서, 화면 상태 전이로 표현한다.**

1. **지속 상태는 지속 표면에** — 데이터 로드 실패는 그 데이터가 놓일 자리에 에러 상태로 렌더한다. 사라지는 알림으로 대체하지 않는다.
2. **순간 확인은 버튼·배지의 상태 전이로** — 복사·취소 접수처럼 짧은 확인은 누른 버튼 자체 또는 인접 배지가 잠시 변했다가 원복한다.
3. **에러는 절대 빈 상태로 위장하지 않는다** — `.catch(() => null)` 후 "없어요" 문구로 떨어지는 것 금지. 에러와 빈 상태는 별도 분기.
4. **모달이 열려 있는 실패는 모달 안에서** — 원인과 재시도가 폼 옆에 있어야 한다.

## 토스트 판단 기준

토스트는 정보 전달력 자체는 좋지만 화면 복잡도와 시선 분산 비용이 있다.
**"액션이 일어난 표면이 결과를 보여줄 수 없을 때"만** 채택한다:

- 액션 직후 그 표면이 사라지고, 도착 화면에도 결과가 보이지 않는 경우
- 사용자가 보고 있지 않은 곳에서 완료되는 백그라운드 작업의 1회성 통지

**현재 admin/pipelines 화면 구성에는 이 조건에 해당하는 케이스가 없다** (실행 성공은 도착 화면의 RUNNING 카드가, 취소는 배지 전이가 확인을 대신). 따라서 각 화면 명세의 "토스트" 열은 전부 "불필요"이며, 아래가 생기면 그때 재검토한다:

- 목록 행에서 상세 진입 없이 실행/취소하는 인라인 액션
- 화면 이탈 후에도 이어지는 장시간 작업의 완료/실패 통지

## 안전망

- 라우트 세그먼트에 `error.tsx`(+ `loading.tsx`) 추가 — 렌더 중 throw가 Next 기본 화면으로 떨어지지 않게 하는 최후 방어선. 표현은 P1과 동일.
- 침묵 삼킴(`.catch(() => {})`)을 유지하는 곳(부가 데이터 degrade)은 반드시 `console.error` 남김.
