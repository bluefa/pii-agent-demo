# 디자인 프로세스 v2 — 기능에서 형태로

> v1(LIN-20 회고)은 캐릭터→시스템→IA 순서로, "어떻게 보일까"에서 시작했다.
> 2026-07-05 오너 지적으로 상류를 추가한다: **누가 이 화면에서 무엇을 하려는지(유즈케이스·
> 태스크)를 정의하지 않고 화면을 다듬고 있었다.** 기간 필터 위치가 두 번 바뀌고, 정보 과다가
> 뒤늦게 발견된 근본 원인. v2는 업계 표준 프로세스(더블 다이아몬드: Discover 발견 → Define
> 정의 → Develop 전개 → Deliver 전달)를 이 저장소의 용어와 게이트로 옮긴 것이다.

## 표준 순서 — 매 작업이 서는 지도

| 단계 | 답하는 질문 | 산출물 | 게이트 |
|---|---|---|---|
| **1. 유즈케이스·태스크** | 누가, 언제, 왜 이 화면에 오나 | `*-usecases.md` — 액터·진입 트리거·태스크 표(빈도×긴급도)·gap | 오너 확인 |
| **2. 정보 구조(IA)** | 태스크에 필요한 정보와 계층은 | `*-info-hierarchy.md` — 정보 인벤토리·T1~X 계층·제외 목록 | 오너 확인 |
| **3. 시스템** | 값(색·크기·간격)은 어디서 나오나 | 캐릭터 선언 · `design-system.md`(치수·표면) · `style-guide.md`(타이포·간격 SSOT) · skill `design-guide` | 취향=실물 비교로 오너 선택 / 측정=기계 audit |
| **4. 레이아웃 시안** | 어떻게 배치되나 | 대표 페이지 variant 2~3종 실제 렌더 비교 | 오너가 고름 — 한 방향 직행 금지 |
| **5. 구현** | — | html/코드 반영 (`*-components.md` 동기화) | — |
| **6. 검증** | 맞게 됐나 | ①기계 audit(스케일 밖 치수 0·콘솔 0) → ②비평(렌더 스크린샷 채점, P0/P1 소진까지) → ③오너 확인 | **오너 승인 후에만 커밋** |

### 운영 규칙

- **턴 선언**: 디자인 작업을 시작할 때 "지금 N단계 작업"을 먼저 밝힌다. 피드백 반영도
  어느 단계의 수정인지 명시한다 — 오너가 프로세스를 따라올 수 있어야 프로세스다.
- **상류 역류 규칙**: 하류 작업 중 상류 질문이 튀어나오면(예: "이 필터 어디 두지?" =
  1~2단계 질문) 화면에서 즉흥 결정하지 않는다. 멈추고 상류 문서를 먼저 고친 뒤 내려온다.
- **취향은 오너가 실물로 고르고, 측정은 시스템 값으로 맞춘다** — 오너에게 백지 질문
  ("어떤 게 좋아요?") 금지, 항상 실물 비교물 2~3개. 측정 가능한 것(크기·대비·자간)은
  묻지 않고 세트 값으로.
- **값은 세트에서만** — skill `design-guide`(오너 가이드 3종: 여백 7원칙·수치 시스템·
  UI 기술 기준) + `admin-pipeline-style-guide.md`. 세트 밖 값이 필요하면 역할을 재검토.

  "정밀하고, 조용하고, 상태색이 주인공".

  치수·표면·anti-slop은 `admin-pipeline-design-system.md`.
