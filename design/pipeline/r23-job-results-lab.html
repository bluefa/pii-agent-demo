R23 시안 랩 — Terraform Job · Condition Job 결과 노출

파이프라인 상세 > Task 패널(Figma 70-35: 실행 정보 · 시도 기록 · 정의·계약 3탭)에 orchestrator가 노출한 job별 실행 결과를 배치하는 시안.
데이터 계약: Task 상세(P5)의 attempts[].terraform_results[](job 결과 메타) · attempts[].job_states[](job 진행 상태) · attempts[].failure_detail · attempts[].check(폴 카운터), 로그 본문은 GET …/attempts/{n}/jobs/{jobId}/result(P11) lazy 조회.

1정보 계층 — 운영자 질문 → 데이터 매핑

detail-ia.md §2의 질문 우선순위를 job 결과에 재적용. 위 계층이 답을 못 주면 아래 계층으로 내려간다.

계층운영자 질문보여줄 정보데이터 소스
L1"이 task 성공했어? 실패했어?" task status pill + 진행 기록 — 기존 그대로, 패널 헤더·실행 정보 탭 상단 TaskDetail.status / started·finished_at
L2"실패했으면 왜?" 실패 원인 스택 — error_code 배지 → failure_detail 텍스트 → 실패 job의 fail_reason. 실행 정보 탭에서 FAILED일 때만 등장 error_code + attempts[].failure_detail + job_states[].last_fail_reason
L3"job 단위로는 어디까지 갔어?" Job 목록 — job별 결과(✓/✕) 또는 진행 상태(원시 state 배지 + 폴 횟수). TERRAFORM_JOB의 실행 정보 탭 본문. CONDITION_CHECK는 판정 요약 kv terraform_results ∪ job_states (job_id로 join) / check
L4"로그 원문 보여줘" 로그 뷰어 — job 행의 [로그] 버튼 → 캔버스 오버레이. 클릭 시에만 fetch(본문 최대 16MB) P11 …/jobs/{jobId}/result → content
L5"이전 시도에선 무슨 일이?" attempt 타임라인 — 시도 기록 탭. attempt 아코디언(최신 확장), 각 attempt 안에 그 시도의 job 목록·failure_detail·response 원문(접힘) attempts[] 전체

핵심 원칙 둘. ① 결과는 attempt에 속한다 — terraform_results·job_states 모두 attempt 스코프의 데이터라서, "현재 상황"(실행 정보 탭)은 최신 attempt만 승격해 보여주고 전체 이력은 시도 기록 탭이 담당한다. ② 본문은 절대 인라인하지 않는다 — 서버가 메타(has_body)만 인라인한 것과 같은 이유로, UI도 [로그] 클릭 시에만 P11을 fetch한다.

3시도 기록 탭 — kind별 이력 구조

두 kind는 시도의 의미가 달라 같은 UI를 쓸 수 없다. TERRAFORM_JOB의 attempt는 "디스패치 1회"(무겁고 적음, job 목록을 품음) → 아코디언. CONDITION_CHECK의 attempt는 "폴 1회"(가볍고 많음, 내용은 판정 하나) → flat 테이블.

4로그 뷰어 (P11) — 캔버스 오버레이

5결정 로그 · 열린 질문

질문결정
job 결과의 1차 표면실행 정보 탭 (최신 attempt 승격) — 실패 시 클릭 0회로 원인 도달. 시도 기록 탭은 이력 전용
job 목록 구성terraform_results ∪ job_states를 job_id로 join. response 원문은 파싱하지 않는다(타입별 사적 계약) — 둘 다 없는 job은 UI가 존재를 모르는 게 계약상 맞다
진행 상태 배지원시 last_state 그대로 mono 배지 — enum 재인코딩·번역 금지 (개념을 줄여라 원칙)
로그 뷰어 표면캔버스 오버레이 (패널 유지). 전체 모달 대비: job 간 이동 시 맥락 유지. 16MB 대비 내부 스크롤, 열 때 tail 시작
두 개의 "없음"content:null(포인터) ≠ 404(행 없음) — empty state 문구를 분리, 각각 다음 행동(메타 신뢰 / error_code 확인)을 안내
RUNNING 중 로그없음이 계약 — foot 안내 한 줄로 정직 노출. 실시간 스트리밍은 서버 측 별도 결정(InfraManager 프록시) 전까지 스코프 밖
CONDITION_CHECKjob UI 미적용 — 판정 요약 kv(실행 정보) + 폴 이력 테이블(시도 기록). 기존 RecordTail의 check kv를 판정 중심으로 재구성
오너 확인 필요:
① ANSI 처리 수위 — 서버는 정규화하지 않는다(설계 §4.6, owner 결정으로 명시). 시안은 "알려진 SGR 색 코드만 렌더 + 나머지 strip"인데, 전부 strip(더 단순)도 가능.
② 16MB 다운로드 — [파일로 저장]은 P11 응답을 blob로 저장하는 클라이언트 구현. 복사만으로 충분하면 뺀다.
③ job_id 표기 — 축약(head…tail) + hover 전문 + 클릭 복사로 가정. 전문 노출이 필요하면 행이 2줄이 된다.
④ Figma 3탭 유지 여부 — 현 앱 패널(R22)은 탭 없이 "진행 기록 + 접힌 정의" 구조. 이 시안은 Figma 3탭을 전제로 그렸다. 탭 없이 가려면 시안 A~C가 곧 패널 본문이 되고 시도 기록은 접힌 섹션으로 들어간다.
