Layout Decision

공간 구조 — 카드 적층 대신 레일 + 패널

v1은 요약 밴드·할 일 카드·타임라인·표를 세로로 쌓아 첫 화면에서 표가 밀려났습니다. 레퍼런스 13곳 중 공간 효율을 해결한 곳은 셋 다 같은 답을 씁니다 — 목록은 한 축에 고정하고, 내용은 패널 하나에서 갈아끼운다.

Elastic Fleet — 패널 하나에서 다단계

정책 선택 → 토큰 → OS별 명령 → 등록 확인까지 플라이아웃 한 장 안에서 진행. 화면 전환·카드 증식이 없다.

레퍼런스 05

Defender — 목록 + 사이드 패널 탭

권장사항 목록은 표 하나로 유지하고, 상세(개요/조치 방법/영향 자산)는 선택 시 열리는 패널의 탭으로. 목록이 화면을 항상 지배한다.

레퍼런스 08

Azure Advisor — 깔때기

타일(요약) → 목록 → 상세로 내려가는 3단. 모든 층위를 동시에 펼치지 않고 한 번에 한 층만 보여준다.

레퍼런스 10
결정: Step 4에는 이미 PR #587의 224px 레일 + 우측 패널 마스터-디테일이 있다. 새 프레임을 발명하지 않고 이 레일을 재사용하되, 레일의 어휘를 "내가 할 일" 그룹(상단) + "BDC 자동 진행" 그룹(하단)으로 재편한다. 우측 패널은 선택된 항목 하나만 렌더 — 할 일이면 값 표·CTA·감지 상태, 자동 단계면 그 단계의 리소스 표. Defender의 그룹핑 토글(작업별↔리소스별)은 별도 토글 없이 레일(작업별) ↔ 전체 요약(리소스별) 선택으로 자연 해소된다. 기존 수치 재사용 원칙(레일 폭·패널 배경)에도 부합.
Design Decisions

화면을 지배하는 6가지 설계 결정

레퍼런스에서 추출한 반복 패턴을 이 화면의 언어로 번역한 것입니다. v2에서 D1이 "카드 승격"에서 "레일 그룹 분리"로 바뀌었습니다.

D1 · v2

레일이 할 일과 자동을 가른다

레일 상단 그룹 "내가 할 일"에 사용자 액션만, 하단 그룹 "BDC 자동 진행"에 시스템 단계. 진입 시 첫 할 일이 자동 선택되어 첫 화면이 곧 해야 할 일이다. 할 일이 0이면 그룹 자체가 "없음"을 말한다.

← Vercel · SES (패턴 1) + #587 레일 재사용
D2

주체 라벨은 3값

"서비스측" 2값 어휘를 폐기하고 담당자 직접 수행 / 서비스 계정에서 자동 / BDC 자동 수행으로 분리. GCP·Azure의 자기모순이 어휘 수준에서 사라진다.

← 감사 구조 문제 ① (side ≠ 실행 주체)
D3

완료 선언의 주어는 제품

할 일에 "완료했습니다" 버튼이 없다. 상태는 감지로 바뀌고, 감지까지의 예상 시간과 "화면을 떠나 있어도 됩니다"를 명시한다.

← Vercel · SES · GitHub Runner (패턴 2·4)
D4

값은 손으로 옮겨 적지 않는다

Source IP 매핑 표·정책 JSON·명령 순서를 표/코드블록 + 복사·다운로드로 제공. 로컬 성공 신호("apply 완료 시 이 출력")까지 알려준다.

← SES · GitHub Runner · Datadog (패턴 3)
D5

표는 작업대다

패널 안 리소스 표에 상태 필터 칩과 설명된 정렬을 붙이고, 상세(단계별 상태·실패 사유 전문·조치)는 행 확장 드로어에. 열은 늘리지 않는다.

← Defender · Dependabot (패턴 5·6)
D6

실수 비용이 큰 액션만 플라이아웃

IDC 방화벽 신청과 AWS Role 부여 두 개만 다단계 플라이아웃(안내 → 값 → 감지 대기 게이트)으로 손잡고 통과시킨다. 나머지는 패널 인라인으로 충분.

← Elastic Fleet · Cloudflare Tunnel

Implementation

구현 계획 — 4개 페이즈

각 페이즈는 독립적으로 머지 가능한 단위입니다. Phase 0은 계약 협의 없이 지금 바로 가능합니다. v2 구조는 기존 레일을 재사용하므로 Phase 1의 공수가 v1 대비 줄어듭니다.

Phase 0

배선 수리 (A안) — 죽은 데이터·코드 잇기

공수 小 · 계약 협의 불필요
  • guides-seed.ts — IDC_STEP_1~7_HTML 배선, STEP_4 공용 HTML을 CSP별로 분리
  • azure/install-detail-adapter.ts — PE id/name 전달 (3줄)
  • AzureInstallationStatus.tsx — 조기 return null → 카드 내 로딩/재시도
  • IdcStep4Installing.tsx — 방화벽 매핑 인라인 복원 (#587 회귀 되돌림), docstring 정리
  • 소비자 4곳 — refresh 소비 + 새로고침 버튼, "마지막 확인" 갱신
  • model.ts — SKIP을 settled에서 분리해 "해당 없음" 상태 신설
Phase 1

레일 재편 (B안·v2) — 2그룹 레일 + 할 일 패널

공수 中(v1보다 감소) · CSP별 콘텐츠 작성 동반
  • install-status-detail/model.ts — InstallTableStep에 kind: 'todo' | 'auto'와 3값 actor 추가, todo용 본문 슬롯(kv표·명령·매핑·cta·waitNote). 레일·패널 렌더 골격은 기존 것 유지
  • InstallStatusDetail.tsx — 레일을 "내가 할 일 / BDC 자동 진행" 2그룹으로 렌더, 진입 시 첫 todo 자동 선택. 헤더에 컴팩트 통계 칩(내 할 일·진행·실패·완료)과 새로고침
  • CSP 어댑터 4개 — todo 정의: AWS(Role 부여 / TF 직접 적용), Azure(PE 승인), GCP(없음 — 그룹 빈 상태), IDC(방화벽 신청)
  • Guide CMS — 스텝 단위 슬롯 키(process.{provider}.4.{step}) 도입, todo 본문을 콘텐츠로 이관
Phase 2

리소스 작업대 (C안) — 전용 표 + 행 드로어

공수 中 · 계약 협의 ①과 병행 시 완성
  • WaitingApprovalTable의 install 변형을 전용 InstallResourceTable로 분리 — 검토 표 파생 구조 청산. Toolbar·Pagination은 재사용
  • 행 확장 드로어 — 단계별 상태 타임라인, 안내 전문(절단 없음), 실패 사유 + 조치 + [다시 확인], IDC는 경로별 성립 상태
  • 상태 필터 칩(전체/진행 중/실패/완료) + 설명된 정렬(실패·조치 필요 우선). 표는 선택된 레일 항목의 컨텍스트를 따른다(그 단계의 상태 열)
  • IDC 식별자를 host:port로 교체, Resource ID 열은 IDC에서 제거
Phase 3

선별 플라이아웃 (D안) — 두 액션만

공수 中 · 감지 API는 계약 협의 ② 이후 완성형

  • 공통 Flyout 셸 — ConfirmStepModal 기준 스펙의 chrome 준수 (모달 통일 부채와 정합)
