01 — 진단

계층이 약한 게 아니라, 계층을 만들 채널을 하나도 안 썼다

근거 등급 — 수치 위반 실측·세트 위반(객관) · UX 원칙 일반 휴리스틱 · 제안 주관 판단.

현재 상태 · paneHead(compact=true)as measured
Terraform 권한 부여 확인
대상 AWS 계정에 Terraform 실행을 위한 IAM Role / AssumeRole 권한이 부여되었는지 검증합니다.
서비스측 확인 진행중

왼쪽은 12/700 제목(이번 라운드에 16/600 으로 올라간다) + 12px 설명. 오른쪽 두 알약은 SideTag 와 집계 상태 알약이다.

D1 여섯 채널 중 여섯이 같다 — 차이는 폭뿐 수치 위반

두 알약을 getComputedStyle 로 재면 면·잉크·크기·무게·높이·라운드가 전부 동일하다. 유일한 차이는 글자 수에서 나온 폭이다. 사람이 "구분할 방법이 없다"고 말한 것은 정확한 관찰이다 — 물리적으로 구분 신호가 0이다.

대비 실측(흰 면 기준): blue-100 면 1.22:1 · blue-800 잉크 8.82:1 (blue-100 위에서는 7.23:1). 대비는 문제가 아니다 — 변별이 문제다.

D2 코드가 쓰려던 단 하나의 레버가 실제로는 안 걸린다 수치 위반

SideTag 는 TABLE_TAG_PILL + 'whitespace-nowrap font-bold' 로 굵기를 한 단 올리려 한다. 그런데 TABLE_TAG_PILL 안에는 이미 textStyles.captionStrong(font-semibold)이 들어 있고, Tailwind 유틸리티는 클래스 나열 순서가 아니라 스타일시트 순서로 이긴다. 실측 font-weight: 600 — font-bold 는 죽어 있다.

결과적으로 지금 화면은 "레버를 하나 썼는데 부족한" 상태가 아니라 아무 레버도 안 쓴 상태다. 이 사실이 중요한 이유: "굵기를 더 올려보자"는 손쉬운 다음 수가 이미 실패한 수라는 뜻이다.

D3 두 값은 종류가 다르다 — 사실과 판정 UX 원칙

side 는 계약 필드 terraform_execution_side(SERVICE/BDC)에서 어댑터가 문구로 옮긴 불변 속성이다. 이 단계가 존재하는 한 절대 안 바뀐다. aggregate 는 aggregateCells() 가 셀 배열에서 매 폴(30s)마다 다시 계산하는 판정이다 — 이 화면에 온 이유 그 자체다.

같은 모양은 "둘 다 같은 빈도로 지켜봐야 한다"고 말한다. 30초마다 바뀔 수 있는 값과 영영 안 바뀌는 값에 같은 주목을 요구하는 것이 계층 붕괴의 내용적 정체다.

D4 두 알약 모두 레일이 240px 왼쪽에서 이미 한 말이다 UX 원칙

DOM 실측 — 같은 화면 레일의 내용:

그룹 밴드 ▸ 내가 할 일 (1)          ← 소유(파란 밴드 = 서비스측 차례)
  항목    ▸ Terraform 권한 부여 확인
            진행중                  ← 판정 (파란 12px 글자, 채운 면 없음)
  항목    ▸ 서비스 측 Terraform 자동 적용 / 진행중
그룹 밴드 ▸ BDC 진행                ← 남색 밴드 = BDC측

페인 머리의 오른쪽 두 알약은 새 정보가 아니라 재진술인데, 화면에서 가장 시끄러운 채널 (채운 칩 두 개)을 쓴다. 레일은 같은 두 사실을 색 있는 글자와 그룹 밴드라는 더 조용한 채널로 이미 말하고 있다.

D5 오너가 이미 내린 결정이 페인 머리에만 미적용 수치 위반

Step 4 레이아웃 v3.1 결정(기록: project_step4_ux_research) — "주체·상태를 필→글자로(색은 실패·진행에만), pane 헤더만 옅은 필 1개".

레일은 이 결정을 구현했다: SideText(칩 폐기, 앞머리 한 단어에만 색), NAV_STATUS_TEXT/NAV_STATUS_WEIGHT(failed·running 만 색+600, 나머지는 gray-700/400). 페인 머리만 칩 두 개가 남았다. 이건 새 디자인 문제가 아니라 한 곳에 안 간 배선이다.

D6 제목이 16/600 으로 커져도 칩끼리의 대비는 그대로 0 제안

실측: 16/600 「Terraform 권한 부여 확인」 = 162.4px, 머리 행 폭 1228px — 공간은 남는다. 제목이 커지면 제목↔칩의 대비는 커지지만 칩↔칩의 대비는 여전히 0이다. 크기 레버는 이 문제를 못 고친다. 다만 제목이 16/600 이 되면 오른쪽 두 칩이 상대적으로 "작은 것 두 개 한 덩어리"로 더 강하게 뭉쳐 보인다 — 문제는 완화되지 않고 악화된다.

D7 가운데 action 슬롯은 죽어 있다 제안

paneHead 우측 그룹은 [SideTag] [action] [상태 알약] 3슬롯인데, InstallTableStep.action 을 채우는 어댑터가 AWS·Azure·GCP·IDC 어디에도 없다. 배치를 바꿀 때 이 슬롯을 그대로 옮겨 다닐 이유는 없다 — 다만 삭제도 하지 않는다(이번 라운드 범위 밖).

02 — 채널 원장

무엇이 팔렸고 무엇이 비어 있나

계층은 채널을 나눠 만든다(feedback_rank_by_splitting_channels: "무게를 한 채널에 몰면 둘 다 1등이 된다"). 그래서 시안을 고르기 전에 쓸 수 있는 채널부터 센다.

채널상태근거
면 (fill)팔림둘 다 blue-100
잉크 (hue)팔림 + 영구 봉쇄둘 다 blue-800. 게다가 판정 알약은 tone 전체를 순회한다(success·info·error·neutral·amber) — 속성에 어떤 계열을 줘도 언젠가 겹친다. feedback_status_pill_owns_every_tone
크기팔림 (바닥)둘 다 12px. 디자인 가이드 폰트 세트의 최소값이라 아래 칸이 없다
무게명목상 팔림, 실사용 0D2 — font-bold 가 안 걸린다. 살려도 600↔700 은 12px 에서 "1px 차이는 계층이 아니라 오차"(design-guide §3)
형태 (칠 vs 획)비어 있음흰 면 + stroke 는 이 줄에서 아무도 안 쓰는 채널 (feedback_white_plus_stroke_survives_both_rows) → 시안 C
위치 (축)비어 있음둘 다 오른쪽 한 줄. 세로 축은 제목·설명이 쓰고 오른쪽 끝은 통째로 비었다 → 시안 B
요소 종류 (칩 vs 글자)비어 있음 (앱 선례 있음)레일이 이미 이 채널로 같은 두 값을 갈랐다 → 시안 A
잉크 채널이 봉쇄된 것이 이 문제의 핵심이다. 상태 알약 하나가 다섯 tone 을 돌려 쓰는 줄에서는 "속성 칩만 다른 색으로" 가 성립하지 않는다 — 정지 화면 한 장에서 안 겹치는 색을 골라도 다른 상태에서 무너진다. 색을 바꾸지 말고 채널을 바꿔야 한다.

03 — 앱 안의 선례

레일은 왜 태그를 버렸고, 페인 머리는 왜 안 버렸나

① SideText — 레일이 이미 내놓은 답 (같은 파일 191행)

legacy 레일의 주석이 이유를 그대로 적어 뒀다: "목차 한 줄에 채운 태그가 둘씩 반복되면 색이 내용을 이긴다. 여기서는 상태도 주체도 글자로 쓰고, 색은 '봐야 하는가'(실패·진행중)에만 남긴다."

SideText 는 side 문자열을 공백으로 쪼개 앞머리 한 단어에만 색을 준다 (sideTextColors.service = blue-800 / .bdc = indigo-800), 뒤따르는 설명은 textColors.secondary 로 남긴다. 정보는 「서비스측/BDC측」에 있고 「확인」·「리소스 생성」에는 없기 때문이다.

왜 레일만 했나: 레일은 항목이 5개라 칩 두 개가 다섯 번 반복됐다 — 반복이 강제한 결정이다. 페인 머리는 한 번뿐이라 같은 압력을 안 받았고, v3.1 결정이 레일에 적용되는 동안 그냥 지나갔다. 한 번이라 안 아팠을 뿐, 규칙이 다른 것은 아니다.

② Step 5 TcHeaderTag — 판정 + 상대시각

5단계 머리에서 판정은 알약 하나(idcStyles.tag.green/red/orange)고, 그 옆의 시각은 12/500 tertiary 글자다. 즉 이 앱은 이미 "채운 알약은 판정 하나만 갖는다"는 문법을 5단계에서 쓰고 있다. 4단계만 그 문법 밖에 있다.

③ 그룹 밴드의 파랑/남색 = 앱의 소유 어휘 (⛔ 지켜야 함)

docs/ux/benchmark/step4-rail-grouping.md:94 — 시안 E 기각 사유가 "라벨의 파랑/남색은 SideTag(서비스측/BDC측)와 같은 색이라 레일과 표가 같은 어휘를 말하고 있었다". 파랑=서비스측 / 남색=BDC측의 색 열쇠는 폐기 대상이 아니다. 세 시안 모두 이 hue 를 유지한다.

⛔ 재제안 금지 — 이 영역의 기각·보류 판례

  • 상태 태그를 카드 머리(바깥)로 올리기 — 오너 보류. 카드 머리 오른쪽은 이미 StampLines 2줄이 쓰고 있고, @1440 실측 없이 금지.
  • 행 확장 드로어 / 상세 모달 재도입 — v3.1 기각.
  • 그룹 라벨 삭제 + 항목별 주체 칩 — step4-rail-grouping.md 기각 판례 3번.
  • full-bleed 회색 트레이 / bgColors.tray — 재도입 금지.
  • 레일 plane 색 변경 — project_guide_rail_hierarchy 의 이중 기각(hover 가 선택행보다 튄다). 이 시안들은 레일을 건드리지 않는다.

04 — 레퍼런스

한 머리에서 소유와 판정을 다른 층에 놓는 일곱 가지 방법

확인함 이번 세션에 실제로 열어 확인 · 기억 기반 학습 지식, 재검증 안 함. 링크는 전부 실주소다.

R1 GitHub Primer — StateLabel vs Label 확인함
https://primer.style/product/components/state-label/

Primer 는 이 구분을 두 개의 다른 컴포넌트로 못 박았다. StateLabel 은 "이슈·PR 의 상태를 렌더링"하는 데만 쓰고 — 아이콘이 붙은 채운 알약, 객체당 하나 — Label 은 "상태·분류·기타 메타데이터를 더하는 시각적 래퍼"로 테두리형이다. 같은 컴포넌트를 색만 바꿔 두 번 쓰는 선택지가 시스템 차원에서 존재하지 않는다.

GitHub PR 머리 (재현)state = 채운 알약 · metadata = 획
● Open chulyonga wants to merge 3 commits
design step-4 needs review

가져올 것 — 판정은 채운 면 + 아이콘, 속성은 흰 면 + 획. 두 종류를 한 부품의 두 색으로 만들지 않는다.

R2 GitLab Pajamas — Badge 확인함
https://design.gitlab.com/components/badge

정의부터가 우리 문제의 언어다 — "배지는 더 큰 객체의 속성으로서 시스템이 생성한 메타데이터를 강조한다." 그리고 쓰지 말아야 할 때를 명시한다: "메타데이터가 강조를 필요로 하지 않으면, 정적 아이콘이나 일반 텍스트를 대신 쓴다."

즉 칩에서 글자로 내려가는 길이 디자인 시스템 차원에서 문서화된 정규 경로다 — 우리 레일이 이미 걸어간 그 길.

가져올 것 — 「강조가 필요한가?」를 칩 여부의 기준으로 삼는다. 서비스측 확인 은 레일 그룹 밴드가 이미 강조했으므로 두 번 강조할 이유가 없다.

R3 AWS Cloudscape — Status indicator vs Badge 확인함
https://cloudscape.design/components/status-indicator/

Cloudscape 의 Status indicator 는 "리소스의 상태를 카드·테이블·목록·헤더 뷰에 쉽게 심을 수 있는 압축된 형태로 전달"한다 — 형태는 아이콘 + 색 글자, 면 없음이다. 반면 Badge(/components/badge/)는 "항목을 라벨링·분류·조직하거나 심각도를 표시하는 색 코드된 작은 요소" — 채운 알약이다.

우리 직관과 반대라는 점이 중요하다. AWS 는 판정을 면 없는 채널에, 분류를 채운 면에 둔다. 면은 "이것이 무엇인가"를, 색 글자는 "지금 어떤가"를 맡는다. 둘이 절대 안 겹치는 이유가 여기 있다.

R4 Atlassian — Lozenge (standard vs subtle) 확인함
https://aui.atlassian.com/aui/6.1/docs/lozenges.html  ·  https://atlassian.design/components/lozenge/

AUI 문서: "주로 상태 표시를 위한 색 글자 로젠지. 표준형과 subtle 변형이 있다." 현행 ADS 는 로젠지를 "사람이 객체를 이해·우선순위화·처리하는 방식에 영향을 주는 의미 있는 속성을 전달하는 두드러진 압축 라벨"로 정의한다.

subtle 변형이 존재하는 이유가 정확히 우리 상황이다 — 한 줄에 로젠지가 둘 이상 필요할 때 하나를 subtle 로 내려 순위를 만든다. 두 개를 모두 bold 로 두는 것이 오용이다.

가져올 것 — 같은 부품을 유지하려면 강도 변형이 있어야 한다. 우리 tagStyles 에는 subtle 계열이 없다 — 그래서 시안 C 는 토큰 신설을 요구한다.

R7 ⚠️ 반증 — Shopify Polaris Badge: 알약 둘이 나란히 서도 된다 확인함
https://ownego.github.io/polaris-vue/components/Badge (Polaris 문서 미러)  ·  shopify.dev/docs/api/polaris

Polaris 주문 화면은 채운 배지 두 개를 나란히 놓는다 — Paid + Unfulfilled. 같은 부품, 같은 크기, 같은 라운드, 색만 다르다. 그리고 잘 작동한다. 문서 정의: "배지는 객체의 tone 또는 취해진 조치를 상인에게 알린다." 작성 규칙: "객체의 tone 을 한 단어로 쓴다. 복잡한 상태를 설명해야 할 때만 두 단어."

Polaris 주문 머리 (재현)같은 층이 맞는 경우
#1008 Paid Unfulfilled

왜 저기서는 되는가 — 전제 두 개. ① 둘 다 같은 종류다: 한 주문의 상태를 이루는 두 면(결제·이행). 둘 다 변하고, 둘 다 지켜볼 값이다. ② 둘 다 한 단어의 tone이다 — 문서가 명시적으로 요구하는 형식. 같은 층으로 읽히는 것이 맞기 때문에 같은 모양이 옳다. 이건 계층 붕괴가 아니라 병렬이다.

여기서는 그 전제가 둘 다 깨진다. ① 서비스측 확인 은 tone 이 아니라 불변 속성이다(D3) — 변하지 않으므로 지켜볼 것이 아니다. ② 한 단어도 아니다: 실제 값은 서비스측 확인·서비스측 리소스 생성·BDC측 리소스 생성·서비스측 승인 — 최장 111.8px 의 구다. Polaris 는 "알약 둘"을 허가하지 않는다 — "같은 종류의 tone 둘"을 허가한다.

가져올 것 — 판정 알약 둘이 필요해지는 날(예: 판정 + 재시도 필요)에는 지금 모양이 정답이다. 그날을 위해 알약 = 판정이라는 슬롯을 비워 둬야 한다.

07 — 추천

시안 A — 주체를 글자로 내린다

머리에 남는 채운 알약은 변하는 값 하나뿐이다 — 주체는 안 변하므로 칩을 내놓고 글자로 내려가고, 소유의 색 열쇠(파랑/남색)만 앞머리 한 단어에 남는다.

표가 A 를 가리키는 이유는 취향이 아니라 세 가지다. ① 진단 6건 중 5건을 덮으면서 신규 토큰 0·신규 컴포넌트 0이다. ② 이 앱이 이미 두 곳에서 쓰는 문법이다 — 레일의 SideText/NAV_STATUS_TEXT, 5단계의 TcHeaderTag(알약 하나 + 맨 글자). 페인 머리만 이 문법 밖에 서 있었다. ③ 오너가 v3.1 에서 이미 내린 결정("pane 헤더만 옅은 필 1개")의 미이행분이다 — 새 방향을 제안하는 게 아니라 안 간 배선을 잇는 것이다.

구현은 <SideTag> → <SideText> 교체 한 지점 (InstallStatusDetail.tsx:724), 컨테이너에 textStyles.caption 한 겹. SideTag 는 소비처가 사라지므로 함께 지운다.

착수 전 확인할 것 하나 — A 의 실패 모드(neutral 판정 옆에서 파란 주체가 더 외침)는 실측으로 판정해야 한다. 확인 링크: AWS 1008(진행중) · 1009(실패) · Azure 1003 · GCP 2009 · IDC 1023. 역전이 실제로 보이면 B 로 승급한다 — B 는 축을 나누므로 tone 전 계열을 견디는 유일한 안이고, 비용은 머리 높이 20px 다. C 는 채택하지 않는다: neutral 에서의 순위 역전이 실측으로 확인됐고 (링 1.80:1 > 면 1.10:1), 그것을 피하려면 토큰을 더 만들어야 한다.

이 라운드에서 하지 않는 것 — 상태 알약을 카드 머리(바깥)로 올리는 안(오너 보류, @1440 실측 필요), action 죽은 슬롯 삭제(범위 밖), 레일 표면·색 변경(기각 판례). 본 문서는 연구용이며 애플리케이션 소스는 수정하지 않았다.
