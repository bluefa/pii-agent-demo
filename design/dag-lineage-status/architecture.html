Monitoring Manager · 설계 검토용

DAG 주간 상태 현황판

Airflow DAG의 OpenLineage 이벤트를 모아, target source 하나에 속한 논리 DB들의 최근 7일 실행 상태를 돌려준다. 설계의 중심 결정은 하나다 — databaseUri를 DAG가 직접 실어 보내므로, 매핑도 배경 동기화도 없다.

우리

Monitoring Manager

이벤트를 수집·저장하고 주간 상태를 응답한다. 이 문서의 대상.

부르지 않음

Pipeline Manager

dagName → databaseUri를 답할 수 있지만 이 설계는 부르지 않는다 — DAG가 자기 databaseUri를 이벤트에 실어 오기 때문.

상류

Infra Manager

targetSourceId → databaseUri 목록. 20x일 때만 유효. 페이징 없음 — 1만 건이 한 응답에.

두 경로

수집과 조회는 서로를 기다리지 않는다

상류를 부르는 지점만 색으로 표시했다. 왼쪽 경로에는 그 색이 하나도 없다 — 상류가 죽어도 이벤트 수집은 멈추지 않는다는 뜻이다.

상류 호출 우리 DB 쓰기

경로 A · 수집

이벤트 → MySQL

상류 호출 0회. ack가 남의 서버 가용성에 묶이지 않는다.

  1. A1

    Composer × N — composite transport

    기존 transport는 그대로 두고 PubSubTransport를 나란히 건다. DAG 수준 + 이름 prefix + databaseUri 有만 통과 (일 240만 → 20만 건). 세 번째 조건에 걸려 버려진 건 로그로 남는다 — 이 설계에서 조용히 샐 수 있는 유일한 지점.

  2. A2

    Pub/Sub topic → pull 구독

    별도 워커 없이 서버 프로세스 안에서 구독. 5회 실패하면 DLQ로.

  3. A3

    dag_run_status ← 멱등 upsert (database_uri 포함)

    run 1건 = 행 1개. 컬럼마다 IF(new.event_time > event_time, …) 가드로 중복·역순 도착을 흡수한다. databaseUri가 이벤트에 있으므로 조회할 게 없다.

상류 호출 0 · 이벤트당 로컬 쓰기 1 · 테이블 1개

경로 B · 조회

GET(targetSourceId) → 주간 결과

목록의 진실은 우리 DB가 아니라 Infra Manager 응답에 있다.

  1. B1

    Infra Manager 호출 → databaseUri 목록

    페이징이 없어 1만 건이 통째로 온다 (최악 ~10MB) → 60초 TTL 캐시로 페이지마다의 재호출을 막는다. 20x가 아니면 조회 실패로 반환하고, 실패는 캐시하지 않는다.

  2. B2

    정렬 후 페이지로 자른다 (예: 100)

    그룹 하나가 최대 1만 개. 이후 단계는 전부 페이지 크기에만 비례한다.

  3. B3

    dag_run_status — WHERE database_uri IN (…) 7일 집계

    (database_uri, logical_date) 인덱스. IN 목록은 100개, 1만 개가 아니다. 날짜 버킷은 도착 시각이 아니라 logical_date의 KST 날짜.

  4. B4

    databaseUri별로 응답

    행이 하나도 없는 databaseUri는 7일 전부 '스케줄 안 됨'.

상류 호출 1 · DB 쿼리 1 (페이지 크기 한도)

DAG가 이미 아는 값이라, 아무도 물어볼 필요가 없다

✓ 이벤트가 databaseUri를 싣고 온다 ✕ 매핑 테이블 · 상류 조회 · 배경 동기화

DAG는 자기가 어느 논리 DB를 처리하는지 알고 있습니다. 그 값을 facet으로 실어 보내면 dag_run_status.database_uri 컬럼 하나로 끝나고, Pipeline Manager 의존 자체가 사라집니다 — 상류가 Infra Manager 하나로 줄어듭니다.

databaseUri가 없는 DAG는 아예 발송하지 않습니다(오너 결정). transport 필터의 세 번째 조건입니다. 덕분에 database_uri는 NOT NULL이고, 소비 경로에 "uri 없는 이벤트" 분기가 존재하지 않습니다.

포기한 것은 하나입니다 — 행이 없을 때 DAG가 안 돎 / 논리 DB에 DAG가 없음 / 이벤트 미도달이 한 픽셀이 됩니다. 화면 요구사항에 'DAG 없음' 상태가 없고 ('스케줄 안 됨'이 이미 정의된 상태입니다) 셋 다 "이 논리 DB는 7일간 아무 일도 없었다"로 참이므로, 구분하지 않는 쪽을 택했습니다.

중요한 건 실패가 관측 가능한 쪽으로 옮겨갔다는 점입니다. databaseUri가 빠진 DAG는 발송 측이 드롭하면서 로그를 남깁니다. 이전 설계에서는 이벤트가 안 닿는 DAG를 Monitoring Manager가 존재조차 알 수 없어 셀 방법이 없었습니다. 지금은 셀 수 있는 곳에서 샙니다.

저장 모델

테이블은 둘뿐이다

dag_run_status

run 1건 = 행 1개. 이벤트 로그가 아니라 최신 상태만. 7일 지나면 삭제.

  • run_id PK · OpenLineage runId. START와 종료 이벤트가 같은 값
  • namespace Composer 환경
  • dag_id DAG 이름 · 환경 간 전역 유니크
  • database_uri NOT NULL · 이벤트 facet에서 온다 · 최대 1024자 · 조회 인덱스 (database_uri, logical_date). utf8mb4면 인덱스 키 3072바이트 한계에 걸려 ascii로 선언
  • logical_date 날짜 버킷 키 (도착 시각 아님)
  • run_type scheduled / manual — 저장만 하고 집계 필터로 쓰지 않음
  • status RUNNING / SUCCESS / FAILED
  • event_time 순서 판정 기준. upsert에서 맨 마지막에 대입

테이블은 이것 하나뿐

두 번째 테이블이 있었다. databaseUri가 이벤트에 실리면서 없어졌다.

  • 매핑 테이블 dag_database_uri — 삭제
  • 명부 미러링 + 단건 resolve — 삭제
  • attempts · 재시도 상한 · batch 상한 · 첫 동기화 소요 — 삭제
  • Pipeline Manager 의존 자체 — 삭제

우리가 저장하는 것

  • ✓7일 창의 run 상태화면이 읽는 창이 곧 보존 기간이다
  • ✓run이 처리한 databaseUrirun 행 안에. 별도 테이블이 아니다

저장하지 않는 것

  • ✕lineage 이벤트 원본보존 요구 없음. 대가는 과거 재계산 불가 — 수용
  • ✕그룹 멤버십 (target_source_id)목록이 변한다. 저장하면 사라진 논리 DB가 남는 상위집합
  • ✕dag 이름 ↔ databaseUri 매핑이벤트가 실어 오므로 들고 있을 이유가 없다
  • ✕그룹별 사전 집계페이지 단위 읽기 시점 GROUP BY로 충분

기각한 대안

왜 더 단순해 보이는 길을 안 갔나

대안기각 사유
이름↔uri 매핑 테이블 + Pipeline Manager 조회 facet이 같은 답을 상류 의존·테이블·동기화 없이 준다. 이벤트로 채우면 맵이 부분집합이라 부재를 해석할 수 없고, 전체 명부를 미러링하면 완전해지지만 그 장치 전부를 유지해야 한다
매 조회마다 Pipeline Manager로 역변환 역방향 조회가 없다. 있더라도 비용이 페이지뷰 수에 비례해 영원히 반복되고 사용자 대기 시간에 얹힌다
멤버십을 우리 DB에 저장 목록이 변한다(논리 DB 소멸). Infra Manager를 어차피 매 요청 부르므로 저장분은 stale 상위집합일 뿐
이벤트에 databaseUri를 facet으로 싣기 ✓ 채택 — 이게 현재 설계다. 아래 "뒤집힌 결정" 참조
이벤트 저장 시점에 databaseUri를 조회 ack가 상류 가용성에 종속되고, 자정 폭주(~330건/s)가 상류로 전파된다. 하루 20만 건의 조회가 통째로 생긴다
dag_run_status 행에 그룹 스탬핑 처리 시점에 그룹을 알 수 없고, 알더라도 수집이 다른 시스템에 결합된다
databaseUri 없는 이벤트를 받아 NULL로 저장 NULL 행은 어느 논리 DB에도 안 붙어 영영 안 읽힌다. 저장할 이유가 없고, 발송 측에서 거르면 최소한 로그가 남는다
전역(비그룹) 주간 보드 유지 진입점이 target source 단위 하나뿐이다. 필요해지면 database_uri distinct를 축으로 되살린다

⛔ 이 축만 네 번 뒤집혔다

① 전체 목록 테이블 + 시간당 sync → ② 이벤트에서 이름 유도 + 미해석분 단건 조회 → ③ 전체 명부 미러링(②는 맵이 부분집합이라 부재를 해석할 수 없다는 이유로 기각) → ④ facet — 매핑 자체를 없앤다.

④를 연 건 두 문장이다: "event 발송 시점에 databaseUri를 같이 실어줄 수 있다" + "없으면 안 보내면 된다". ③이 사려던 "DAG가 있긴 한가"라는 구분은 화면 요구사항에 없었고, ③이 막으려던 은폐는 발송 측 로그가 더 싸게 막는다.

다시 열려면 확인할 것 — 화면에 'DAG 없음'을 '스케줄 안 됨'과 다르게 표시해야 하는가. 그렇다면 명부가 다시 필요하다.

검토 포인트

여기가 틀렸으면 설계가 틀린다

전부 계약이 아직 확인 안 된 가정이다. 하나라도 다르면 알려주면 된다.

01

행이 없는 databaseUri를 '스케줄 안 됨'으로 그리는 게 맞나

이 설계에서 가장 중요한 가정이다. 지금은 DAG가 안 돎 / 논리 DB에 DAG가 없음 / 이벤트 미도달을 한 픽셀로 그린다. 셋 다 "7일간 아무 일도 없었다"로 참이라 택했다. 구분이 필요하면 명부 미러링이 다시 필요해진다.

02

페이지 정렬 기준이 databaseUri 사전순이다

화면이 다른 순서(이름순, 최근 실패순)를 원하면 페이지네이션 방식이 달라진다 — 정렬 키가 우리 DB에 없는 값이면 1만 건을 다 받아 정렬해야 한다.

03

facet 이름·경로가 아직 안 정해졌다

설계 전체가 이벤트에 실린 databaseUri에 걸려 있다. 커스텀 job facet으로 잡아뒀지만 tags facet이면 목록에서 꺼내야 한다. 양쪽에 seam을 한 곳씩만 뒀으니 확정되면 메서드 둘만 고친다.

04

databaseUri 없는 DAG를 안 보내는 게 맞나

발송을 막는 쪽을 택했다 — 받아서 NULL로 저장하면 어차피 안 읽히는 행만 쌓이고, 발송 측에서 거르면 로그가 남는다. 대신 그 로그가 유일한 신호라 알람을 걸어야 한다.

05

논리 DB 하나를 DAG 두 개가 처리할 수 있나

집계가 GROUP BY database_uri라 그런 경우 두 DAG의 실행이 한 행으로 합쳐지고, 표시되는 dag 이름은 MAX(dag_id) 하나뿐이다. 합치는 게 맞는지, 아니면 나눠야 하는지.

미결

답이 오면 바로 반영할 것

비-20x는 무슨 뜻인가

지금은 전부 조회 실패로 반환한다. 404가 "target source 없음"이면 그것만 빈 화면으로 분기해야 한다.

facet 누락 드롭에 알람을 걸 것인가

prefix에 걸리는데 databaseUri가 없는 DAG는 화면에서 영영 안 보인다. 지금은 발송 측 log.warning 한 줄이 유일한 신호다 — 로그 기반 지표로 올릴지 정해야 한다. 이 설계에서 조용히 사라질 수 있는 유일한 경로다.

10MB 응답을 실제로 받아봤나

1만 건 × 최대 1KB. HTTP 타임아웃과 메모리 여유, 그리고 TTL 60초가 화면 조작 속도에 맞는지 함께 본다.

databaseUri가 정말 ASCII인가

인덱스 키 3072바이트 한계 때문에 ascii로 선언했다. 한글 등이 섞이면 인덱스를 해시 컬럼으로 옮겨야 한다.
