Monitoring Manager · 설계 검토용

DAG 주간 상태 현황판

Airflow DAG의 OpenLineage 이벤트를 모아, target source 하나에 속한 논리 DB들의 최근 7일 실행 상태를 돌려준다. 설계의 중심 결정은 하나다 — 수집은 상류 서버를 한 번도 부르지 않고, 조회는 매번 부른다.

우리

Monitoring Manager

이벤트를 수집·저장하고 주간 상태를 응답한다. 이 문서의 대상.

상류

Pipeline Manager

전체 DAG 이름 목록을 한 번에. 그리고 dagName → databaseUri — 이쪽은 단건만, 역방향 없음. 50 병렬까지 허용.

상류

Infra Manager

targetSourceId → databaseUri 목록. 20x일 때만 유효. 페이징 없음 — 1만 건이 한 응답에.

두 경로

수집과 조회는 서로를 기다리지 않는다

상류를 부르는 지점만 색으로 표시했다. 왼쪽 경로에는 그 색이 하나도 없다 — 상류가 죽어도 이벤트 수집은 멈추지 않는다는 뜻이다.

상류 호출 우리 DB 쓰기

경로 A · 수집

이벤트 → MySQL

상류 호출 0회. ack가 남의 서버 가용성에 묶이지 않는다.

  1. A1

    Composer × N — composite transport

    기존 transport는 그대로 두고 PubSubTransport를 나란히 건다. DAG 수준 + 이름 prefix만 통과 (일 240만 → 20만 건).

  2. A2

    Pub/Sub topic → pull 구독

    별도 워커 없이 서버 프로세스 안에서 구독. 5회 실패하면 DLQ로.

  3. A3

    dag_run_status ← 멱등 upsert

    run 1건 = 행 1개. 컬럼마다 IF(new.event_time > event_time, …) 가드로 중복·역순 도착을 흡수한다.

상류 호출 0 · 이벤트당 로컬 쓰기 1 · 매핑에 관여하지 않는다

경로 B · 조회

GET(targetSourceId) → 주간 결과

목록의 진실은 우리 DB가 아니라 Infra Manager 응답에 있다.

  1. B1

    Infra Manager 호출 → databaseUri 목록

    페이징이 없어 1만 건이 통째로 온다 (최악 ~10MB) → 60초 TTL 캐시로 페이지마다의 재호출을 막는다. 20x가 아니면 조회 실패로 반환하고, 실패는 캐시하지 않는다.

  2. B2

    정렬 후 페이지로 자른다 (예: 100)

    그룹 하나가 최대 1만 개. 이후 단계는 전부 페이지 크기에만 비례한다.

  3. B3

    dag_database_uri — WHERE database_uri IN (…)

    databaseUri를 dag 이름으로 되돌린다. IN 목록은 100개, 1만 개가 아니다.

  4. B4

    dag_run_status — 7일 집계

    (dag_id, logical_date) 인덱스. 날짜 버킷은 도착 시각이 아니라 logical_date의 KST 날짜.

  5. B5

    databaseUri별로 응답

    매핑이 없는 databaseUri는 7일 전부 '스케줄 안 됨'. 이름을 몰라도 답이 나온다.

상류 호출 1 · DB 쿼리 2 (둘 다 페이지 크기 한도)

두 경로 밖 · 1시간 주기

DagDatabaseUriSync

Pipeline Manager의 전체 DAG 이름 명부를 그대로 미러링한다. 수집도 조회도 여기에 걸려 있지 않아서, 막혀도 이벤트는 계속 쌓이고 화면은 계속 뜬다.

  • 1단계 · 명부전체 DAG 이름 목록을 1콜로 받아 통째로 INSERT IGNORE
  • 2단계 · 해석database_uri IS NULL인 이름만 단건 조회 — 벌크가 없어서 50 병렬, 한 주기 2000건
  • 왜 명부인가맵이 완전해야 "매핑 없음"이 "DAG 없음"이라는 사실이 된다. 이벤트에서 이름을 얻으면 맵은 부분집합이고, 부재가 무엇을 뜻하는지 말할 수 없다
  • 빈도매핑이 1:1 불변이라 2단계는 DAG 하나당 평생 1회. 새 DAG가 없는 주기는 명부 1콜로 끝
  • 실패attempts를 올리고 다음 주기 재시도, 상한(5)에서 정지
  • 첫 동기화명부 전체가 미해석 — 10만 건이면 (10만/2000) 주기. 이때만 무는 상한이다

역방향이 없으니, 명부를 통째로 들고 있는다

✓ dagName → databaseUri ✕ databaseUri → dagName

조회 중에 모르는 databaseUri를 만나도 그 자리에서 상류에 물어 채우는 lazy 캐시가 될 수 없습니다 — 물어볼 방향이 없기 때문입니다. 그래서 맵은 미리 채워져 있어야 하고, 문제는 무엇으로 채우느냐였습니다.

이벤트로 채우면 맵은 실제로 돌았던 DAG만 덮는 부분집합이 됩니다. 그러면 "맵에 없다"가 두 가지를 동시에 뜻합니다 — DAG가 없거나, 이벤트가 우리에게 닿지 않았거나. 후자는 transport 오설정·prefix 오타· Composer 환경 누락인데, 화면에는 평온한 '스케줄 안 됨'으로 나옵니다. 저희 시스템은 그 DAG들이 존재한다는 것조차 모르니 알람도 못 겁니다.

전체 이름 명부를 미러링하면 맵이 완전해지고, 그제서야 부재가 사실이 됩니다. 남는 창은 지난 주기 이후 새로 만들어진 DAG 하나뿐입니다.

저장 모델

테이블은 둘뿐이다

dag_run_status

run 1건 = 행 1개. 이벤트 로그가 아니라 최신 상태만. 7일 지나면 삭제.

  • run_id PK · OpenLineage runId. START와 종료 이벤트가 같은 값
  • namespace Composer 환경
  • dag_id DAG 이름 · 환경 간 전역 유니크
  • logical_date 날짜 버킷 키 (도착 시각 아님)
  • run_type scheduled / manual — 저장만 하고 집계 필터로 쓰지 않음
  • status RUNNING / SUCCESS / FAILED
  • event_time 순서 판정 기준. upsert에서 맨 마지막에 대입

dag_database_uri

역방향 맵 하나만 담는다. 그룹 컬럼은 없다.

  • dag_name PK · 수집 경로가 INSERT IGNORE로 남긴다
  • database_uri UNIQUE · 최대 1024자 · sync가 채우기 전까지 NULL. utf8mb4면 인덱스 키 3072바이트 한계에 걸려 ascii로 선언
  • attempts 해석 실패 횟수. 상한에서 재시도 정지
  • seen_at 이름을 처음 본 시각
  • resolved_at databaseUri를 채운 시각

우리가 저장하는 것

  • ✓7일 창의 run 상태화면이 읽는 창이 곧 보존 기간이다
  • ✓dag 이름 ↔ databaseUri역방향 조회가 없어서 우리가 들고 있어야 한다
  • ✓전체 DAG 이름 명부위 맵과 같은 테이블. 완전해야 부재가 사실이 된다

저장하지 않는 것

  • ✕lineage 이벤트 원본보존 요구 없음. 대가는 과거 재계산 불가 — 수용
  • ✕그룹 멤버십 (target_source_id)목록이 변한다. 저장하면 사라진 논리 DB가 남는 상위집합
  • ✕그룹별 사전 집계페이지 단위 읽기 시점 GROUP BY로 충분

기각한 대안

왜 더 단순해 보이는 길을 안 갔나

대안기각 사유
이벤트에서 이름을 유도해 맵을 만든다 맵이 부분집합이 되어 부재를 해석할 수 없다 — DAG 없음과 이벤트 미도달이 같은 픽셀. 전체 목록이 가능해진 이상 택할 이유가 없다 (2회 뒤집힌 결정)
매 조회마다 Pipeline Manager로 역변환 역방향 조회가 없다. 있더라도 비용이 페이지뷰 수에 비례해 영원히 반복되고 사용자 대기 시간에 얹힌다 — 명부 미러링은 DAG당 평생 1회
멤버십을 우리 DB에 저장 목록이 변한다(논리 DB 소멸). Infra Manager를 어차피 매 요청 부르므로 저장분은 stale 상위집합일 뿐
이벤트에 databaseUri를 facet으로 싣기 검토 중 — 기각 아님. DAG가 이미 아는 값이라 조회가 없다. 채택하면 매핑 테이블·sync·resolve가 통째로 사라진다. 대신 "이 논리 DB에 DAG가 있긴 한가"를 못 답한다 — 명부는 그 구분을 사려고 있는 장치다
이벤트 저장 시점에 databaseUri를 조회 ack가 상류 가용성에 종속되고, 자정 폭주(~330건/s)가 상류로 전파된다. 하루 20만 건의 조회가 통째로 생긴다
dag_run_status 행에 그룹 스탬핑 처리 시점에 그룹을 알 수 없고, 알더라도 수집이 다른 시스템에 결합된다
전역(비그룹) 주간 보드 유지 진입점이 target source 단위 하나뿐이고, 전역 목록의 원천이 사라졌다

한 건은 되살렸다. "이벤트에서 이름 유도 + 미해석분만 단건 조회"는 앞선 리뷰에서 이벤트 0건 DAG가 화면에서 사라진다는 이유로 기각됐었다. 목록 축이 Infra Manager로 옮겨간 지금은 그 부작용이 없어서 다시 채택했다.

검토 포인트

여기가 틀렸으면 설계가 틀린다

전부 계약이 아직 확인 안 된 가정이다. 하나라도 다르면 알려주면 된다.

01

매핑이 없는 databaseUri를 '스케줄 안 됨'으로 그리는 게 맞나

지금은 "그 논리 DB의 DAG가 한 번도 안 돌았다"로 읽는다. 만약 "아직 DAG가 만들어지지 않았다"와 "DAG는 있는데 안 돌았다"를 화면에서 구분해야 하면 상태가 하나 더 필요하다.

02

페이지 정렬 기준이 databaseUri 사전순이다

화면이 다른 순서(이름순, 최근 실패순)를 원하면 페이지네이션 방식이 달라진다 — 정렬 키가 우리 DB에 없는 값이면 1만 건을 다 받아 정렬해야 한다.

03

삭제된 DAG의 매핑 행은 지우지 않는다

DAG가 사라져도 dag_database_uri에 행이 남는다. 10만 규모라 무해하다고 보고 정리 배치를 두지 않았다 — 이 판단이 괜찮은지.

04

sync 주기 1시간이 적당한가

새로 만들어진 DAG가 명부에 들어오기까지의 창이다. 그 사이 그 DAG가 돌면 화면은 '스케줄 안 됨'으로 보인다. DAG를 얼마나 자주 만드는지에 달렸다.

05

이벤트가 실제로 논리 DB당 DAG 1개로 떨어지나

1:1이 아니라면 database_uri의 UNIQUE 제약이 깨지고, 한 논리 DB의 여러 DAG를 어떻게 합칠지가 새 질문이 된다.

미결

답이 오면 바로 반영할 것

비-20x는 무슨 뜻인가

지금은 전부 조회 실패로 반환한다. 404가 "target source 없음"이면 그것만 빈 화면으로 분기해야 한다.

명부 응답 크기와 단건 호출 지연

명부는 매 주기 받는 유일한 대형 응답이다. 단건은 병렬 50이 확정됐지만 1건이 100ms면 한 주기 2000건이 4초, 1초면 40초 — 첫 동기화 소요를 정한다. 명부가 databaseUri까지 같이 준다면 단건 조회는 통째로 사라진다.

10MB 응답을 실제로 받아봤나

1만 건 × 최대 1KB. HTTP 타임아웃과 메모리 여유, 그리고 TTL 60초가 화면 조작 속도에 맞는지 함께 본다.

databaseUri가 정말 ASCII인가

인덱스 키 3072바이트 한계 때문에 ascii로 선언했다. 한글 등이 섞이면 UNIQUE를 해시 컬럼으로 옮겨야 한다.
