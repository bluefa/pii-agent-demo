승인 대기는 표의 행이 아니다

1차 시안이 "여전히 형편없다"는 평가를 받았습니다. 밖에서 승인 화면 네 개를 직접 열어 보고 나니 이유가 분명해졌습니다 — 1차는 전부 "무엇을 더 크게 쓸까"만 답했고, 넷 중 어느 것도 승인 대기 건을 표의 행으로 그리지 않습니다. 이 문서는 레퍼런스 4종과, 거기서 나온 시안 2안입니다.

Why R1 failed

1차 시안이 틀린 지점

1차 진단(면 대비 1.05:1 · 등급 역전 · 빈 바닥 212px)은 측정값이라 여전히 유효합니다. 틀린 건 처방입니다.

1차가 한 것 숫자를 32px로 키우고, 격자를 2:1로 바꾸고, 오른쪽 카드의 크롬을 벗겼습니다. 전부 "같은 표를 어떻게 더 크게 쓸까"였습니다. 표는 표로 남았고, 요청 한 건은 여전히 텍스트 다섯 칸입니다.
밖에서 하는 것 승인 대기 건을 객체로 그립니다 — 얼굴(아바타·타일)이 있고, 카드거나 간격으로 띄운 덩어리이고, 결정 버튼이 그 안에 있습니다. 넷 중 어느 것도 표의 행이 아닙니다.
① External references

외부 레퍼런스 4종

브라우저로 직접 열어 확인한 것들입니다. 마케팅 히어로 아트가 아니라 실제 화면 구조가 보이는 것만 골랐습니다.

Reference 1

Earnify — Affiliate Applications Management

가장 가까움

승인 대기 신청을 2단 카드로 깝니다. 카드 하나 = 신청 하나이고, 안에 아바타 + 이름 + 출처, 작은 라벨 상자로 묶은 근거 수치 3개, 인용문으로 뜬 Application Note, 그리고 카드 오른쪽 아래 [Approve] [Reject]가 들어 있습니다. 위에는 4칸짜리 요약 스트립이 있는데 타일 4장이 아니라 한 컨테이너를 세로선으로 나눈 것입니다.

가져올 것 — ① 요청 하나 = 카드 하나, 결정이 카드 안에. ② 요약은 한 표면을 칸으로 나눈다 — 이러면 1차에서 기각한 "타일 4장"의 문제(표면 4개)를 피하면서 수치는 준다. 시안 D의 뼈대.
Reference 2

AdminHub — Purchase Request Approval

구조가 우리와 같음

다크 사이드바 + 라이트 본문으로 우리 셸과 구조가 같고, 사이드바의 "My Approvals"에 붉은 건수 배지 4가 붙어 있는 것까지 같습니다. 본문은 브레드크럼 → 큰 제목 + 상태 pill → 승인 단계 가로 스텝퍼 → 왼쪽 본문 카드(사실을 2열 key-value 격자로, Justification은 "Read more"로 접음) → 우측 레일(Request Summary · Approval History 세로 타임라인 · Request Actions 링크 목록) → 맨 아래 Approval Decision 블록(Approve/Reject/Request Changes를 색 점 달린 아웃라인 pill 셋으로, 그 아래 코멘트 입력).

가져올 것 — ① 사실은 나열 문장이 아니라 2열 kv 격자. ② 결정을 명시적 블록으로 — 버튼 두 개를 구석에 두지 않고 "여기서 결정한다"는 자리를 만든다. ③ 우측 레일이 요약·이력을 받는다. 시안 E의 뼈대.
Reference 3

Krispy (Equal) — Creators / Waiting for approval

승인 대기자 목록을 간격으로 띄운 미니 카드 스택으로 그립니다. 헤어라인 표가 아니라 카드가 gap으로 떨어져 있고, 각 카드에 좌측 색 스트라이프(사람마다 다른 색)와 아바타가 붙습니다. 카드 안은 두 줄뿐입니다 — 이름, 그리고 "Waiting for approval".

가져올 것 — 헤어라인을 gap으로 바꾸면 목록이 표가 아니라 객체 더미로 읽힌다. 그리고 항목마다 색 앵커가 하나 있어야 목록이 평평해지지 않는다 — 우리에겐 이미 그 앵커가 있다(서비스 레일의 해시 색 타일). 지금 권한 요청 화면만 그걸 안 쓴다.
Reference 4

Noviq — Pending Approvals

가장 단순한 형태. 카드 안의 목록인데 행마다 아바타가 있고 행 오른쪽 끝에 [Approve] 버튼이 있습니다. 상세로 나가는 링크가 아니라 그 자리에서 끝냅니다.

가져올 것 — 승인함의 최소 조건. 이것보다 적으면 "목록"이지 "승인함"이 아니다. 지금 우리 화면은 이 최소 조건도 없다 — 행을 누르면 다른 페이지로 나간다.
② The rule

넷의 공통점

승인 대기 건은 표의 행이 아니라 얼굴과 결정을 가진 객체다.

넷 다 (1) 항목마다 색 앵커가 있고, (2) 헤어라인이 아니라 간격·카드로 떨어져 있고, (3) 결정이 목록 안에 있습니다. 우리 화면은 셋 다 없습니다 — 그래서 "흰 바탕에 흰 카드"로 보이는 겁니다. 카드가 안 보이는 게 아니라 카드 안에 아무 형태도 없어서입니다.

1차 진단과의 관계 1차에서 잰 값(면 토큰 전부 1.41:1 안쪽)은 그대로입니다. 다만 결론이 달라집니다 — 면으로 강조가 안 되면 형태로 만든다. 간격 · 모서리 · 타일 색 · 카드 그림자는 대비값을 안 쓰고도 덩어리를 만듭니다. 1차는 그 자리에서 "타입을 키우자"로 갔고, 그건 같은 평면을 더 크게 쓴 것뿐이었습니다.
③ Alternative D

시안 D — 요청 카드 스택 추천

Reference 1 + 3. 승인 대기 목록을 표에서 카드 스택으로 바꾸고, 카드를 리세스 바닥 위에 띄웁니다. 카드는 기본 접힘, 누르면 그 자리에서 펼쳐져 사유와 결정 버튼이 나옵니다.

앵커없음 — 첫 칸이 Knox ID 텍스트서비스 타일 34px(해시 색)레일·검색·시트가 이미 쓰는 마크다. 같은 서비스가 어디서나 같은 얼굴로 읽힌다. 새로 만드는 색이 아니다.

결정다른 페이지펼치면 사유 인용 + [반려][승인]Ref 1·4. 펼칠 때만 상세 1회 호출이라 N+1이 아니다.

시안 D와 비교해 얻는 것
  • 사유를 자르지 않고 읽는다 — 펼침 카드는 폭이 좁아 긴 사유가 부담스럽다.
  • 왼쪽 목록이 짧아 6건이 한 화면에 다 보이고, 오른쪽이 세로를 다 쓴다(빈 바닥 해소).

  • 제품 안 선례가 가장 많다 — Step4 · IDC 요청 조회 · 서비스별 권한이 전부 이 골격.
비용 · 리스크
  • 목록에서 하나를 골라야 내용이 보인다 — 6건을 훑어 우선순위를 잡는 데는 D가 낫다.
  • 상세 페이지(/requests/[id])와 역할이 겹친다. 딥링크는 이 화면의 선택 상태로 흡수하는 편이 낫다(URL에 requestId).
  • 기본 선택을 뭘로 할지 결정 필요 — 첫 건 자동 선택 vs 빈 상태.
