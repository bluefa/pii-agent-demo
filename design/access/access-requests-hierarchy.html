내 권한 요청 — 왜 힘이 없는가, 무엇을 강조할 것인가

/access-requests 화면이 "강약이 없다 · 좌측에 쏠렸다"는 평가를 받았습니다. 두 지적은 별개 문제이고, 둘 다 원인이 한 줄로 특정됩니다. 제품 안 5개 화면과 이미 검증된 외부 벤치마크 9종의 결론을 근거로 시안 3안 + 기각 1안을 제시합니다.

Executive Summary

결론 먼저

"평평하다"는 색·굵기의 문제가 아니라 구조의 문제입니다. 같은 바닥에 놓인 형제 카드 2장은 무슨 등급을 매겨도 형제로 읽힙니다. 그리고 좌측 쏠림은 관리자 전용 레이아웃 토큰을 사이드바 없는 화면에서 쓴 결과입니다.

결론 1

시선이 처음 닿을 곳이 없다

화면 최대 타입이 h1 24px 하나뿐이고 그 아래는 전부 18/16/14. 같은 제품의 연동 요청 화면은 헤더 문장 안에 32px primary 총계를 심어 "지금 몇 건이 나를 기다리는가"를 먼저 말합니다. 이 화면엔 그 문장이 없습니다.

결론 2

형제 2장은 등급을 못 만든다

테두리·그림자·크기가 동일한 카드가 1fr 1fr로 나란히 있습니다. 대칭 2열은 "이 둘은 짝"이라는 선언입니다. 08-12 확정 워크벤치에서 채널을 나눠 등급을 줘도 평평했던 것과 같은 실패이며, 해법도 같습니다 — 표면 수를 줄인다.

결론 3

좌측 쏠림은 토큰 오용 1줄

layout.content의 max-w-[1440px]에는 mx-auto가 없습니다. 관리자 화면에선 216px 다크 사이드바가 오른쪽으로 밀어 줘서 가운데로 보였을 뿐입니다. 사이드바가 없는 이 화면에선 그대로 왼쪽 벽에 붙습니다.

Diagnosis

① 현재 화면 진단

지적 두 개를 각각 코드까지 내려가 원인을 특정합니다.

1-1. 좌측 쏠림 — flex-1이 아무 일도 하지 않는다

app/access-requests/layout.tsx는 관리자 섹션의 콘텐츠 토큰을 빌려 씁니다.

pipelineStyles.layout.content = 'flex-1 min-w-0 max-w-[1440px] px-8 pt-6 pb-12'

이 토큰은 /admin/pipelines/** 전용입니다. 거기서는 layout.shell(display:flex) 안에서 216px 다크 사이드바 오른쪽에 놓이므로, 1440 블록이 화면 중앙 쪽으로 밀려 균형이 잡힙니다. /access-requests의 부모는 <body>이고 body는 flex 컨테이너가 아닙니다 — flex-1은 무효, mx-auto는 없음, 결과는 좌측 정렬된 1440 블록입니다.

교정 이 화면 전용 콘텐츠 클래스를 두고 mx-auto를 붙인다. 폭은 1440이 아니라 1200이 맞다 — 사이드바가 빠진 만큼 콘텐츠가 넓어질 이유는 없고, 행 스캔 콘텐츠가 아니라 목록 두 개짜리 화면이다.

1-2. 강약 없음 — 원인 네 가지

#원인근거해법
a 판정이 화면에 없다 사용자가 이 화면에 오는 이유는 "내 요청 승인됐나?"인데, 그 답은 오른쪽 카드 표 안의 11px pill 하나에만 있다. 헤더는 기능 설명만 한다. 판정을 헤더 문장으로 끌어올린다 (32px 총계 + 상태 메타 줄)
b 형제 2장 = 평평 같은 바닥에 놓인 같은 크롬의 상자 둘. 계층은 포함에서 생기지 등급에서 생기지 않는다(RULE 10). EUI도 형제 패널은 서로 닮아야 한다고 규정한다 — 형제로 놓는 선택 자체가 순위를 포기하는 것. 테두리 있는 표면은 1개(조작 대상만). 기록은 바닥에 직접 놓고 헤어라인으로만 나눈다 (RULE 11)
c 타입 램프가 두 칸 24 → 18 → 16/14 뿐. 두 카드 제목이 같은 18/600이라 "둘 다 1등"이 된다. 램프를 세 칸으로: 29~32(판정 수치) → 16/600(작업 면 제목) → 14/600(기록 라벨). RULE 14
d primary CTA가 0개 이 화면의 유일한 행동인 [요청]이 variant="secondary" size="sm". 화면에서 가장 중요한 버튼이 가장 약한 버튼이다. 행 CTA를 primary로. 화면당 primary 1종은 유지된다(다른 primary 없음)
Benchmark

Alternatives

③ 시안 3안

세 안 모두 폭 교정(mx-auto)과 헤더 판정 문장을 공유한다. 갈리는 지점은 "요청 목록과 내역을 어떤 구조로 놓을 것인가"다.

시안 A

판정 헤더 + 작업면 1장 + 바닥 기록 권장

표면을 1개로 줄인다. 판정은 헤더 타입으로, 조작 대상(요청할 서비스)만 테두리 있는 카드로, 기록(내 요청 내역)은 바닥에 직접 놓고 헤어라인으로만 나눈다. 세 요소가 세 개의 다른 평면에 있으므로 등급을 매기지 않아도 순위가 생긴다.

좋은 점
  • 표면 1개 — RULE 11을 정확히 만족. 세 평면(타입 / 카드 / 바닥)이 곧 세 등급.
  • 재방문자의 질문("승인됐나?")에 스크롤 없이 답한다.
  • 2열 그리드로 한 화면에 서비스 10개 → 폭이 실제로 일을 한다.
  • 기존 부품만 쓴다. PagedCard에 이미 bare prop이 있고(시트용), 기록 쪽이 바로 그 모드다.
비용 / 리스크
  • 세로로 길어진다. 1440×900에서 기록 표 하단이 접힘 아래로 내려간다 — 다만 기록은 2순위라 의도된 순서다.
  • 요청 0건인 첫 방문자에겐 헤더 수치가 비어 다른 문장이 필요하다(문안 아래 §적용 참고).
  • [권한 요청] primary가 행마다 6개 → 색 면적이 커진다. hover에만 primary, 평상시 secondary로 완화 가능.
시안 B

레일 + 시트 — 접근 권한 3화면과 같은 골격

이 기능의 관리자 화면(서비스별 권한)이 이미 쓰는 골격을 그대로 요청자 쪽에 적용한다. 좌측 296px 레일에 서비스(+내 권한 상태), 우측 시트에 선택한 서비스의 내 상태·요청 이력·CTA.

좋은 점
  • 접근 권한 4개 화면이 하나의 골격으로 통일된다. 관리자↔요청자가 같은 화면 문법을 배운다.
  • 풀블리드라 좌측 쏠림이 구조적으로 불가능해진다.
  • 서비스 하나를 기준으로 "내 권한 · 요청 상태 · 사유 · 이력"이 한 자리에 모인다.
비용 / 리스크
  • 전체 내역을 한눈에 못 본다. "내가 뭘 요청했더라"가 서비스별로 흩어진다 — 요구사항 ④(승인 내역 조회)와 정면으로 충돌.
  • 첫 방문자는 아무것도 선택되지 않은 빈 시트를 본다. 요청 흐름의 시작이 "고르기"가 아니라 "찾기"인데 레일은 훑기용 부품.
  • 요청은 보통 1~2건인데 20행 레일은 과설계. Cloudscape도 split view는 상세 페이지를 대체하지 말라고 한다.
  • 구현량이 가장 크다(레일 상태·라우팅·시트 4슬롯).
시안 C

비대칭 2열 — 작업면(1.35fr) + 리세스 기록(1fr)

2열은 유지하되 대칭을 깬다. 왼쪽은 테두리+그림자의 카드(조작 대상), 오른쪽은 면에 파인 홈(리세스, 그림자 없음, 12px 라벨 헤더). 폭도 1.35 : 1 — "짝이 아니다"를 폭으로 먼저 말한다. 리세스 색은 표준 #F2F4F7이 아니라 #E9EBF3이다(이유는 리스크 첫 항목).

좋은 점
  • 세로 길이가 현재와 같다. 두 목록이 한 화면에 남는다.
  • 변경량이 가장 작다 — 그리드 비율 + 오른쪽 카드의 크롬 교체.
  • 기록이 좁아지며 열이 3개로 줄어 오히려 읽기 쉬워진다(사유는 행 아래 줄로).
비용 / 리스크
  • 표준 리세스가 이 화면에선 안 먹힌다. 목업을 그려 보고 발견한 것이다 — 리세스 표준값 #F2F4F7은 이 페이지 바닥 #F4F4FB(body 배경)와 사실상 같은 밝기라 홈이 보이지 않는다. 리세스는 흰 시트를 파낼 때 성립하는 장치인데 이 화면엔 팔 시트가 없다. 쓰려면 #E9EBF3 정도로 한 단 더 내려야 하고, 그만큼 그 위 텍스트의 대비 여유가 깎인다.
  • 여전히 같은 바닥의 형제 둘이다. 08-12에 "채널을 나눠도 형제면 평평"을 이미 겪었다 — 리세스가 깊이를 만들어 주긴 하지만 A만큼 확실하진 않다.
  • 기록의 열이 줄어 "결과·사유" 전문이 잘린다.
Rejected

기각안 — 상단 요약 버킷 3장

가장 먼저 떠오르는 안이고, 실제로 이 제품에 선례(운영 알림 4버킷)가 있어서 기각 사유를 남긴다.

기각 사유. 운영 알림에서 버킷이 성립한 이유는 버킷 하나가 서로 다른 작업 큐의 진입점이기 때문이다(누르면 다른 목록으로 간다). 여기서는 세 수치가 전부 같은 표 하나를 가리키므로, 버킷은 아래 표가 이미 말하는 사실을 반복하면서 표면 수만 셋 늘린다. 같은 사실을 두 표면에 쓰지 않는다(RULE 8), 사실이 셋을 넘으면 카드가 아니라 열이다(RULE 12) — 그 "열"이 시안 A의 승인 2 · 반려 1 메타 한 줄이다.

Apply

권장안과 적용 수치

시안 A를 권장한다. 폭 교정은 어느 안을 고르든 동일하게 선행한다.

1. 폭 교정 공통

app/access-requests/layout.tsx에서 pipelineStyles.layout.content 대신 mx-auto w-full max-w-[1200px] px-8 pt-6 pb-12. 관리자 토큰은 사이드바를 전제하므로 이 화면이 빌려 쓰면 안 된다는 주석을 남긴다.

2. 헤더 판정 문장 P0

queue/requests의 문법을 그대로 옮긴다 — 14px 문장 + text-[32px] font-bold text-[var(--pl-primary)] 인라인 수치 + 도착 전 스켈레톤. 우선순위는 반려 > 대기 > 없음: 반려가 있으면 "반려된 1건이 있어요 — 사유를 확인하고 다시 요청할 수 있어요", 없으면 대기 건수, 요청이 0건이면 "아직 요청한 권한이 없어요. 아래에서 서비스를 골라 요청해 보세요".

3. 표면 1개로 P0

내역 카드를 PagedCard bare로 바꿔 바닥에 놓는다(이미 있는 prop, 서비스별 권한 시트가 쓰는 모드). 제목은 18/600 → text-[14px] font-semibold text-[var(--pl-text-medium)]. 요청 카드만 a.card 유지.

4. CTA 승격 P1

행 버튼 variant="secondary" → "primary", 라벨 요청 → 권한 요청. 화면에 다른 primary가 없어 예산은 1종을 유지한다.

5. 서비스 목록 2열 P2

카드 본문을 grid grid-cols-2 gap-x-6, 페이지당 5 → 10행. 1200px 폭에서 한 행이 594px이라 타일+이름+코드+버튼에 적정하다. 이걸 안 할 거면 폭을 1200 → 1000으로 줄이는 편이 낫다.

바뀌지 않는 것

  • 서비스 행 문법(타일 · 이름 · 코드 태그) — 방금 /services 레일과 맞춘 것이라 그대로 둔다.
  • 검색(300ms 디바운스, 코드·이름, 서버 질의) — 그대로.
  • 요청 모달, 계약, mock — 손대지 않는다. 이 문서의 제안은 전부 레이아웃과 타입이다.
